# People: implementation plan

**Spec:** [`docs/specs/people.md`](../specs/people.md). Read it first; this plan only orders the work
and names the files and tests. Nothing here starts before the owner accepts the spec and its
"Conflicts with the code".

**Shape.** Ten server tasks, each one PR. Each PR passes `dotnet test` with the speaker model present
(CI fetches it), uses synthetic audio only (invariant 6), a fake `ISpeakerEmbedder` returning set
vectors and a hand-written `ILlmClient`, and changes the README sections of what it touches
(endpoints, variables, MCP tools, "What it stores") in the same PR.

## Migrations, allocated up front

Numbers are fixed now so tasks in separate worktrees never pick the same one. A migration is never
edited once merged. DbUp runs every unjournaled script in name order, so a later number merging
first is fine where the table says the two are independent.

## P-1: segment links and the label rule

Migration `0014_people_links.sql`: `people.note text null check (length(note) <= 500)`;
`segments.person_id uuid null references people on delete set null` with a partial index;
`people_runs` as the spec's "What it stores".

1. `Nytka.Storage/PeopleStore.cs`: `SpeakerLabel.Joins` adds `left join people sp on sp.id =
   s.person_id`; `Column` becomes `case when {IsUser} then 'Wearer' else coalesce(sp.name, p.name,
   s.speaker) end`; a new `PersonId` expression `coalesce(s.person_id, pv.person_id)`. A person's
   segment count is by the `PersonId` expression (a segment counts for the person it shows, through the voice or
   its own link); `UnnamedVoicesAsync` leaves out segments with `person_id`.
2. `ConversationStore.cs:219` and `ExportStore.cs:123` use `SpeakerLabel.Joins` instead of their own
   join, and read `personId` and `personName` through the new expressions.
3. `Api/PeopleEndpoints.cs`: `PATCH /people/{id}` takes `name?` and `note?` (at least one); `PeopleStore.RenameAsync` becomes `UpdateAsync`. `MergeAsync` in the store also moves
   `segments.person_id`.
4. `Api/VoiceEndpoints.cs` (`PATCH /segments/{id}`): accepts `personId` (a person id or null) next
   to `isUser`; either may be absent; 404 for an unknown person.
5. New `Server/People/PeopleExtensions.cs` (`AddNytkaPeople`, called from `Program.cs`) and
   `People/PeopleSettings.cs` (empty group for now). `/api/v1/info` features gain `people`.
6. Tests: a segment with `person_id` shows that name over its voice's person and the provider's
   label, in the conversation API, the MCP transcript, the memory prompt input and the export; the
   wearer still wins; deleting the person brings the voice's name back; merge moves segment links; a
   read token gets 403 on the PATCH.
7. README: the `PATCH /segments/{id}` row changes and a `PATCH /people/{id}` row is new (the table has no
   people rows today); `/info` lists `people`; "Speaker labels" names the three steps; "What it stores" names
   the note and the segment link.

## P-2: name suggestions (Layer 1)

Migration `0015_name_suggestions.sql` (without the `group_id` constraint; P-6 adds it).

1. `People/NameSuggestionTrigger.cs`: `IEventSubscriber` on `conversation.ready`, as
   `MemoryTrigger`, checking `people.suggestNames`, the model, brief length and that an unnamed
   target exists; marks `people_runs (names)` pending and queues `suggest-names` (Ai lane).
2. `People/SuggestNamesHandler.cs`: renders targets as `Voice A`, `Voice B` and lines with `#id`;
   the prompt and schema in `People/NamePrompt.cs`; applies the spec's drop rules; retries as
   `ExtractMemoriesHandler` (three rounds an hour apart).
3. `Nytka.Storage/NameSuggestionStore.cs`: read targets, insert with `on conflict do nothing`,
   list, accept (one transaction: `speaker` writes `person_voices` through `PeopleStore`'s SQL,
   `label` writes `segments.person_id` on that batch's segments that have no person yet; `group` answers 409 until P-6),
   reject. Accepting also deletes the other pending rows of the same target. The unique index is on the target
   (`speaker_id`, `group_id`, or a label's lowest segment id) and `lower(name)`: the table has no batch or label column.
4. Routes in `Api/PeopleEndpoints.cs`: `GET /people/suggestions` (`status` defaults to `pending`; newest 200), `POST .../accept`,
   `.../reject` (404 for an unknown id, 409 when not pending).
5. `people.suggestNames` in `PeopleSettings`, `.env.example`, `docker-compose.yml`.
6. Tests: a self-introduction in a fake answer becomes one pending suggestion with the evidence
   segment; a suggestion naming the wearer's `memories.userName`, a letter not sent, a segment of
   another conversation or confidence 0.4 is dropped; accept on `speaker` labels every segment of
   that voice; accept on `label` labels only that batch's segments; a rejected name is not
   inserted again; a repeated `conversation.ready` with no new segments makes no model call; no
   segment changes label before accept.
7. README: a "People" section (Layer 1 in short), API rows, the setting.

## P-3: person facts (Layer 3)

Migration `0016_person_facts.sql`.

1. `People/FactTrigger.cs` and `People/ExtractPersonFactsHandler.cs`, modelled on
   `MemoryTrigger` and `ExtractMemoriesHandler`; `people_runs (facts)`. The input lists the
   conversation's confirmed people and known people named in a line (case-insensitive whole word),
   by `FactBasis.Involved`, which the trigger also uses to decide whether there is anyone to write
   about. A wearer's line is the wearer's whatever person is set on it, so its basis is `about`.
2. The basis table of the spec in one static method, `FactBasis.Of(segment, personId, personName)`,
   unit-tested without a database.
3. `Nytka.Storage/PersonFactStore.cs`: apply (fingerprint per person, tombstones), list, add,
   edit, delete; `PeopleStore.MergeAsync` moves facts, dropping the merged person's duplicates.
4. Routes: `GET`, `POST /people/{id}/facts`, `PATCH`, `DELETE /people/{id}/facts/{factId}`.
5. `NytkaEvent.PersonFactCreated` (`person.fact.created`); `WebhookRecorder` type and payload.
6. `people.facts` setting.
7. Tests: a fact whose evidence is the person's own line is `said`, the wearer's line `about`, an
   unconfirmed speaker's line naming the person `mentioned`, the same line without the name dropped;
   a deleted fact is not re-added; an edited one is never rewritten; deleting the conversation
   deletes its facts; the webhook payload has no transcript; a read token cannot write.
8. README: a "Facts about people" section after "Memories" (P-2 owns "People"), the `people.facts` setting,
   API rows, the event in "Webhooks", "What it stores".

## P-4: tasks owed to a person

Migration `0017_task_person.sql`: `tasks.person_id uuid null references people on delete set null`.

1. `Ai/ConversationPrompt.cs`: the task item becomes `{ text, person }` in `Schema`; the user
   message (`User` and `UserForMerge`) gets a `People:` line with the conversation's confirmed
   non-wearer people, read from `SegmentRow.PersonId` and `PersonName` (the label rule, so P-1's
   segment links count once merged); `SystemForMerge` keeps the shape. `ConversationAnswer.Tasks`
   becomes a list of `AnswerTask(Text, Person)`; `LlmJson` needs no change (it already accepts a
   null property and rejects a null array element).
2. `EnrichConversationHandler.StoreAsync` and `TaskStore.ReconcileAsync`: `AiTask` gains
   `PersonId`, set on insert only, from a name equal (ignoring case) to a listed person.
3. `TaskStore`, `TaskEndpoints`: Task gains `personId`, `personName`; `PATCH` accepts `personId`
   (`null` clears it, an unknown person is 404, and a change marks the task `edited`).
   `McpTaskItem` and `McpTaskRow` (their own copies of the query) gain the same two fields, so MCP
   `list_tasks` and `get_conversation` follow `TaskRow`. The webhook `TaskData` is unchanged.
4. Tests: a fake answer with `person: "Olena"` and Olena among the speakers sets `person_id`; an
   unknown name leaves null; an existing task keeps its person on a re-run; deleting the person
   nulls it; an old-shape answer (strings) fails validation and retries as today.
5. README: Task fields in the API table and "Tasks".

## P-5: person page, MCP and search

Migration `0018_people_search.sql`: `search tsvector` with GIN and null-partial indexes on `people`
(name, weight A) and `person_facts` (text, weight B); stale triggers as 0007's;
`create or replace function nytka_search_setup` with the body of 0007 plus the two tables in the
clearing step.

1. `PeopleStore.ViewAsync` (the store takes `PersonFactStore` and `TaskStore` for the facts and tasks):
   last seen (the newest segment by the label rule's person, never the wearer's), newest 10
   conversations, newest 50 facts, newest 100 open tasks with `person_id`, voices, note,
   `hasVoiceprint` and `voiceprintSamples`. `GET /people/{id}`. `SummariesAsync` serves `list_people`.
2. The indexer (`SearchStore.IndexPendingAsync`, run by `SearchDictionarySync`) gains the two tables;

3. `People/PeopleTools.cs`: `list_people` (no REST twin), `get_person` (`id` or `name`; REST's page
   without `hasVoiceprint` and `voiceprintSamples`, as the spec says); `SearchTools` accepts `person`. The full tool list in `SearchToolTests` gains the two names.
4. Tests: the view's fields; `search?q=` finds a person by name and by fact, hides a deleted fact;

   what REST returns minus the two voiceprint fields; no vector field appears, `hasVoiceprint` is the

5. README: API rows, "MCP", "Search".

## P-6: voice groups and voiceprints (Layer 2, server core)

Migration `0019_voice_groups.sql`: `voice_groups`, `person_voiceprints`, `voice_matches`;
`segment_fingerprints` gains `group_id` (set null) and `grouped boolean not null default false`;
the `name_suggestions.group_id` foreign key (cascade).

1. `Nytka.Storage/VoiceGroupStore.cs`: ungrouped fingerprints (not the wearer's, no person, model
   given), groups and voiceprints of a model, assign, new group, add to match, delete empty groups,
   confirm (links, blend, delete group, one transaction), forget all. Reuses `VoiceStore.Encode`,
   `Decode`, `Blend` (`Blend` is private today: make it `internal`).
2. `People/GroupVoicesHandler.cs` (Audio lane, `group-voices`): the spec's three steps with
   `SpeakerEmbedder.Cosine`; `Scheduler` queues it each minute when the setting is on, the model is
   loaded and an ungrouped row exists.
3. Retention: `BatchStore.DeleteSpeechAudioEndedBeforeAsync` deletes groups left empty in the same
   statement; `VoiceStore.ForgetAsync` deletes every group.
4. `PeopleStore.DeleteAsync` relies on cascades; `MergeAsync` blends voiceprints of the same model.
5. Settings `people.voiceMatching` and `people.voiceThreshold`; the setting response refuses `true`
   with "Enroll your voice first" when no voiceprint exists (a `Conflicts` check cannot see the
   table, so the endpoint checks). `/api/v1/info` gains `voice-groups` when on, model loaded and
   retention at least 1.
6. `GET /api/v1/people/voice-eval` and `DELETE /api/v1/people/voiceprints`.
7. Tests: two sets of fake vectors 0.9 apart in cosine form two groups; a vector at 0.75 to a
   voiceprint becomes a pending match and changes no label; the wearer's segments are never grouped;
   setting off queues nothing; retention removing the last fingerprint deletes the group; deleting a
   person leaves no `person_voiceprints` row; retention 0 produces no group; no route's JSON
   contains a vector (assert on keys and response size); a thrown error in the job leaves
   transcription untouched.
8. README: "People" Layer 2, the privacy paragraph, "What it stores", settings.

   Pure function over rows, unit-tested.
2. Clip: frames of the stretch's first 10 s cut by capture time from `speech_audio`

   (invariant 1).
3. Routes `GET /people/cards`, `GET .../clip`, `POST /people/cards/{kind}/{id}`. A `group`
   suggestion of P-2 now accepts through the same confirm.
4. Tests: a 4 s stretch is not offered, 6 s is, with a 6 s clip; a 30 s stretch gives a 10 s clip;

5. README: cards in "People", API rows.

## P-9: calendar and briefs

Migration `0020_calendar.sql`: `calendar_events`, `briefs`.

1. ICS parsing: add `Ical.Net` after checking its licence and its .NET 10 support (both UNKNOWN as
   of this plan; a hand-written parser without recurrence is the fallback, and the spec then drops
   recurring events). `Calendar/IcsReader.cs` returns events of the next 48 h with `CN` names.
2. `Calendar/SyncCalendarHandler.cs` (Hooks lane, `sync-calendar`): a named `HttpClient` like the
   webhook one (`AllowAutoRedirect = false`, 10 s), a 5 MB read cap, the URL never logged. Upsert
   events, delete those ended over a day ago with their briefs.
3. `Calendar/MakeBriefHandler.cs` (Ai lane, `make-brief:{uid}:{start}`): queued by the scheduler for
   events within `calendar.briefMinutes` with a matched person and no brief; prompt from the P-5
   view (facts, note, open tasks, last 5 titles and summaries); stores and publishes `brief.ready`.
4. `Calendar/CalendarSettings.cs`: `calendar.icsUrl` (`SettingType.Secret`),
   `calendar.briefMinutes`. `Api/BriefEndpoints.cs`: `GET /briefs/upcoming`.
5. Tests: an ICS fixture written in the test (synthetic names) with a weekly event yields the right
   instances in `Europe/Kyiv` across a DST change; a 302 fails the sync without following it; a
   6 MB body fails; an attendee "olena" matches person "Olena"; no matched person, no brief; the
   brief prompt holds no transcript line; `brief.ready` payload shape; the URL never appears in a
   captured log.
6. README: "Calendar briefs" with the privacy note (titles and names go to the model), settings,
   API rows, the event; `NOTICE` if the library needs it.

## App (android, not designed here)

- **People tab** (or a section of an existing tab; the five-tab bar is the app's decision): people
  by last seen, search, add.
- **Person page:** note, facts with add, edit and delete, open tasks, recent conversations, forget.
- **Who-is-this cards:** play the clip, pick a person or type a name, skip, "not a person"; shown
  only when the server lists `voice-groups`.
- **Review inbox:** one list of the three kinds with accept and reject.
- **Consent chime:** an app setting, off by default, that plays a short chime on the phone every N
  minutes (5 to 60) while capturing. It is not a server setting and changes nothing about capture.
- Voice matching switch with the legal-duty sentence, and the calendar brief notification from
  `brief.ready` or a poll of `/briefs/upcoming`.

## Review focus

1. **Suggestions stay suggestions.** Only accept routes write `person_voices`, `segments.person_id`
   or a voiceprint; tests assert labels before and after.
2. **Vectors.** Grep each diff for `Encode(`, `bytea` and vector-typed DTO fields; only Postgres
   gets one, no group outlives its last fingerprint, and forgetting a person leaves no row.
3. **Facts' basis** comes from the evidence segment in server code.
4. **Lanes.** Model calls in Ai, grouping in Audio (no network), calendar fetch in Hooks; nothing
   new runs inside `transcribe`.
5. **Migrations** keep their allocated numbers; 0018 restates all of `nytka_search_setup()`.
6. **Logs.** No calendar URL, fact, name suggestion or transcript text in a log line.
