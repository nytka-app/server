# Tags and roles: implementation plan

**Spec:** [`docs/specs/tags.md`](../specs/tags.md). Read it first; this plan only orders the work and
names the files and tests. Nothing here starts before the owner accepts the spec and its "Conflicts
with the code".

**Shape.** Seven server tasks, each one PR. Each PR passes `dotnet test`, uses a hand-written
`ILlmClient` and synthetic names, logs no tag name, and changes the README sections of what it touches
(endpoints, variables, MCP tools, "What it stores") in the same PR.

## Migrations, allocated up front

Numbers are fixed now so tasks in separate worktrees never pick the same one. A migration is never
edited once merged. On `main` at `4ef9667` the last is `0020_calendar.sql`, and no open branch adds one.

## T-1: tags, links and filters

Migration `0021_tags.sql`: `tags` (`id uuid primary key`, `name text not null unique` with a check of
1 to 32 characters, `created_at`); `conversation_tags` and `person_tags` (composite key, both foreign
keys `on delete cascade`, `created_at`, index on `tag_id`); a function and two `after delete ... for
each statement` triggers that delete tags with no link in either table.

1. `Nytka.Storage/TagName.cs`: `Normalize(string) -> string?` by the spec's rules, and `Display(string)`
   ("dog-walker" to "Dog walker"). Unit tests without a database: Latin, Cyrillic, `#`, spaces, 33
   characters, `a/b`, a leading `-`.
2. `Nytka.Storage/TagStore.cs`: list with counts (and `q` prefix), tags of conversations and of people
   by id list (one query, joined in C#, as `PeopleStore.ListAsync` does for voices), add (find or
   create the tag, insert the link `on conflict do nothing`, 20-per-item check under `for update` of
   the item), remove, rename, merge, delete. Static helpers taking a connection and transaction, so
   T-4 and T-6 add tags inside their own transactions.
3. `ConversationStore.ListAsync` takes `tag` (an `exists` on `conversation_tags`); `ConversationSummary`
   and `ConversationDetail` gain `Tags`. `MergeIntoAsync` moves `conversation_tags` to the survivor
   (`insert ... select ... on conflict do nothing`) before it deletes the others.
4. `PeopleStore.ListAsync` takes `tag`; `PersonRow` and `PersonView` gain `Tags`. `MergeAsync` moves
   `person_tags` the same way.
5. `Api/TagEndpoints.cs` (`MapTags`): `GET /tags` (read), rename, merge, delete. `PUT`/`DELETE` on
   `/conversations/{id}/tags/{name}` in `ConversationEndpoints.cs` and on `/people/{id}/tags/{name}`
   in `PeopleEndpoints.cs`. Problem titles are fixed sentences and never contain the name.
   A `?tag=` that is no valid name is `400`; deleting an unknown tag is `404`. The hosting log line "Request
   starting" holds the request path and so the name: `Program.cs` sets `Microsoft.AspNetCore.Hosting.Diagnostics` to
   Warning (the test host replaces Serilog, so its log capture skips that category and logs at Information).
6. `WebhookRecorder`: `ConversationData` gains `Tags`.
7. `/api/v1/info` features gain `tags`. `PostgresFixture` truncates `tags`.
8. Tests: add, add again (one link), remove, remove absent (200); `Робота` and `#робота` are one tag;
   `a/b` is 400; the 21st tag is 409; filters return only tagged items and page as before; deleting a
   conversation, a person, the last link, and merging two conversations and two people leave no unused
   tag and lose no link; rename to a taken name is 409; merge unions links; a read token gets 403 on
   every write; `conversation.ready` payload carries `tags`; a captured log of the whole test holds no
   tag name.
9. README: a "Tags" section after "People", API rows, "What it stores".

## T-2: search and MCP

1. `SearchStore.SearchAsync` takes `tag`: the conversation and person CTEs join the link tables when it
   is set, memories are skipped. `SearchEndpoints` and `SearchTools` pass `tag` (normalized; an invalid
   one is 400 or an MCP error).
2. `Mcp/McpTags.cs`: `list_tags`. `list_conversations` (`McpTools`, `McpQueries`) and `list_people`
   (`PeopleTools`) take `tag`; their items, `get_conversation` and `get_person` carry `tags`.
   `list_people` reads `PeopleStore.SummariesAsync(tag)`, whose `PersonSummary` gains `Tags`, and
   `list_conversations` and `get_conversation` read `McpQueries`, whose rows gain `Tags`. `list_tags`
   takes `query` (as the `search` tool does; REST calls it `q`) and shares `TagEndpoints.ListForAsync`
   with the route. A bad `tag` gives the fixed sentence in `TagEndpoints.InvalidTagSentence`.
3. `SearchToolTests`' full tool list gains `list_tags`.
4. Tests: `search?q=&tag=` keeps tagged conversations and people, drops memories; MCP answers equal the
   REST ones for the same filter.
5. README: "Search", "MCP".

## T-4: proposed tags for conversations

Migration `0022_tag_suggestions.sql`: `tag_suggestions` as the spec; unique on
`(coalesce(person_id, conversation_id), name)`; a partial index on `created_at desc where status =
'pending'`, and plain indexes on `conversation_id` and (where set) `person_id` for the cascades.

1. `Tags/TagSettings.cs` (`tags.suggest`, `true`), registered as a settings group; `.env.example`,
   `docker-compose.yml`.
2. `Ai/ConversationPrompt.cs`: `tags` in `Schema`, in `ConversationAnswer`, in the system message and
   the merge message; a `Tags:` line in `User` and `UserForMerge` from `TagStore` (100 most used) when
   the setting is on and the conversation is not brief (`TagStore.NamesInUseAsync`).
3. `EnrichConversationHandler.StoreAsync`: normalizes, drops tags the conversation has and names of
   people it lists (or a word of one), keeps 3, inserts `tag_suggestions` `on conflict do nothing` in the same
   transaction. A brief conversation stores none.
4. `Nytka.Storage/TagSuggestionStore.cs`: list, accept (adds the tag through `TagStore` in one
   transaction; 409 at 20), reject. `MergeIntoAsync` and `PeopleStore.MergeAsync` move every row, not only
   pending ones, so a rejected name stays rejected for the survivor (`on conflict do nothing`; the
   leftovers go with the cascade).
5. Routes `GET /tags/suggestions`, `POST .../accept`, `.../reject`; `ReviewStore` gains kind `tag`
   (`proposal.tag`), `ReviewEndpoints` routes it; the item's `text` is the conversation's summary. `/api/v1/info` features gain
   `tag-suggestions`.
6. Tests: a fake answer with `["Work", "work", "olena"]` and Olena in the people line stores one
   proposal `work`; nothing is linked before accept; reject then a re-run stores nothing; removing an
   accepted tag and a re-run stores nothing; setting off sends no `Tags:` line and stores nothing; an
   answer without `tags` fails validation and retries; the inbox lists and answers it.
7. README: "Tags" (proposals), the setting, API rows, the privacy sentence.

## T-5: proposed tags for people

1. `ExtractPersonFactsHandler`: `tags: [{ personId, tag }]` in `Schema`, `Answer` and the system message;
   the `Tags:` line as T-4; drops a tag for a person not sent, more than 3 per person, or one the person
   has; stores through `TagSuggestionStore` in the facts transaction.
2. Tests: a tag for a sent person is a pending proposal with that person and the source conversation; a
   tag for an id not sent is dropped; the inbox shows the person's name; accept tags the person, not the
   conversation.
3. README: "Facts about people" one sentence.

## T-6: roles

Migration `0023_roles.sql`: `people.named boolean not null default true`; `name_suggestions` gains
`role text null`, `named boolean not null default true`; the `target` check also allows `person`; drop
and recreate `name_suggestions_target_name` keyed on
`coalesce(speaker_id, group_id::text, person_id::text, segment_ids[1]::text)` for `person` targets
(write the expression so existing rows keep their keys: `person_id` counts only when `target = 'person'`).

1. `People/NamePrompt.cs`: schema (`name` and `role` nullable), system message, `Voice A (known as:
   repairman)` lines. `People/NameTargets.cs`: segments of a person with `named = false` form a target
   `person` (`NameSegment` gains `PersonId` and `PersonNamed`, read in `ReadInputAsync`).
2. `SuggestNamesHandler.Apply`: role normalized by `TagName`; drop when neither name nor role; a
   role-only candidate gets the display form as name and `named = false`.
3. `NameSuggestionStore.AcceptAsync`: the four cases of the spec's table. A role-only accept calls a new
   `PeopleStore.CreateNumberedAsync(display)` ("Repairman", "Repairman 2", ...), never
   `FindOrCreateAsync`; a role adds the tag through `TagStore`; a `person` target renames, or merges into
   the person of that name. `PeopleStore.UpdateAsync` sets `named = true` with any name.
4. API: suggestion items, review proposals and people gain `role` and `named`; MCP `list_people` and
   `get_person` and the export's `person` line gain `named`; `/info` gains `roles`.
5. Tests: "the repairman is here" fake answer gives a role-only suggestion named "Repairman"; accept
   creates "Repairman" with tag `repairman` and `named = false`; a second accept elsewhere creates
   "Repairman 2"; a later run proposes "Mykola" for that person's voice and accept renames them and keeps
   the tag; a name equal to an existing person merges; an answer with role "майстре" stores what the
   model sent after normalization (no stemming on the server); neither name nor role is dropped; a
   rejected role is not offered again; no label changes before accept.
6. README: "People" (roles), API rows, "Export" (`named`); `docs/specs/export.md` the field.
