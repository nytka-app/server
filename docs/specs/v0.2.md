# Nytka v0.2: the AI layer

**Status: draft.** The whole picture lives in [../vision.md](../vision.md); version 0.1 is
[v0.1.md](v0.1.md).

Version 0.2 makes the server read what it hears. Each conversation gets a title, a summary and tasks
from a language model you pick, speaker names pass through from the transcription answer, agents
read everything over a read-only MCP endpoint, and the app edits server settings and creates named
tokens. This spec covers both repositories, `nytka-app/android` and `nytka-app/server`. The frame
wire format, the `/api/v1` style, the RFC 9457 error shape and `apiVersion: 1` stay as in v0.1;
every change adds to the API, so a v0.1 app keeps working against a v0.2 server.

## Done when

1. A closed conversation gets a title, a summary and tasks within three minutes (a fake model in the
   tests), and the app shows them.
2. A model answer that breaks the schema fails the attempt. Three failures leave `aiStatus: failed`;
   an hour later the server tries again, three rounds at most.
3. A conversation that grows after it was summarized is summarized again once it closes: a title you
   set stays, and tasks you completed, edited or deleted are neither duplicated nor brought back.
4. `segments[].speaker` from the transcription answer shows as `speaker`; without it, null.
5. Tasks can be listed, completed, reopened, edited and deleted over the API and in the Tasks tab.
6. A `read` token calls the endpoints the API table marks `read`, and MCP, and gets `403` on all
   others; a revoked token gets `401` on its next request; the environment token works on an empty
   database.
7. A setting resolves as its environment variable (an empty one counts as unset), else its table
   row, else its default. Environment-supplied settings are `locked` and refuse writes (`409`); a bad
   value is a `400` naming the key; a changed `llm.model` applies to the next job without a restart.
   API keys come only from the environment: `GET /settings` reports `isSet`, never a value, a `PATCH`
   naming one gets `409`, and no key reaches the database, a response or a log.
8. The official MCP client connects to `/mcp` with a `read` token, finds its three tools by name
   (v0.4 adds more) and gets from each the data REST returns. `POST /mcp` with no token, or a
   revoked one, gets `401`, in a test of its own.
9. While a fake model holds a request open for a minute, a new chunk is still transcribed.
10. `GET /status` reports a failure only while it is current: once a later batch transcribes,
    `lastError` is null and `lastSuccessAt` is later than `lastErrorAt`.
11. The server boots on a v0.1 schema, which has no `settings` table (nothing reads settings before
    the migrator has run), and migrates it without data loss; its conversations show `aiStatus: none`.
12. On a phone: five tabs; a conversation shows title, summary, tasks and colored speakers; a ticked
    task stays ticked after a refresh; developer mode changes `llm.model` and creates and revokes a
    token; a `read` token typed in gets "The app needs an admin token."
13. CI is green in both repositories, and the docs cover every new variable and endpoint.

## Scope

**In:** titles, summaries and tasks from an OpenAI-compatible chat endpoint; renaming; the Tasks API
(list, complete, edit, delete: control over data derived from your speech); speaker labels; the
read-only MCP endpoint; server settings in the app; named tokens with scopes; the five-tab app.

**Out:** memories, search and webhooks (v0.4); offline sync (v0.3); due dates and hand-made tasks (a
task's text carries its deadline); summaries of open conversations; matching anonymous speaker labels
across batches; OAuth for MCP; prompts edited at runtime.

## Tokens and scopes

Every request under `/api` and `/mcp` carries `Authorization: Bearer <token>`.

- **The environment token**, `Nytka__AdminToken`, is always `admin`, is compared in constant time and
  is never stored, listed or revoked: the break-glass token, so a broken database cannot lock you out.
- **Named tokens** come from an `admin` caller with a name (1 to 64 characters, unique among active
  tokens, case-insensitive) and a scope. A token is `nyt_` plus 43 base64url characters (32 random
  bytes); the server keeps its SHA-256, a hint (the last four characters) and its times, and shows
  the token once, in the create answer. Lookups use no cache, so a revoked token fails at once.

`admin` may call everything. `read` may call `/mcp` and the endpoints marked `read` below; an
endpoint without the mark needs `admin`, so new endpoints are closed by default. `401`: token
missing, unknown or revoked (`WWW-Authenticate: Bearer`). `403`: valid token, too little scope. The
app reads `scope` from `/api/v1/info` and refuses a `read` token ("The app needs an admin token."); a
server without `scope` counts as `admin`.

## Settings

A setting resolves in this order: its environment variable when that is set and not empty, else its
row in the `settings` table, else its default. An empty environment variable counts as unset, so a
Compose file can pass every optional variable through empty without shadowing the table. A setting is
`locked` when the environment supplies it, and `PATCH` refuses it with `409`. A change reaches the
next job or request without a restart. The table is read only after the migrator has run: before
that, and on a database without a `settings` table, the environment and the defaults apply. The
admin token and the database connection are never settings. A key's environment variable is
`Nytka__` plus the key with each `.` as `__` and each part capitalized (`llm.baseUrl` is
`Nytka__Llm__BaseUrl`).

| Key | Type | Default | Validation |
|---|---|---|---|
| `stt.url` | url | | Absolute http or https URL. Always locked: the server refuses to start without it. |
| `llm.baseUrl` | url | | As `stt.url`, without query or fragment; the server calls `{baseUrl}/chat/completions`. |
| `stt.apiKey`, `llm.apiKey` | secret | | Environment only: listed read-only, never written. |
| `stt.model`, `llm.model` | string | | Up to 128 characters. |
| `stt.language`, `llm.outputLanguage` | language | `auto` | `auto` or a tag such as `uk` or `en-GB` (`^[a-z]{2,3}(-[A-Za-z0-9]{2,8})*$`); for `llm.outputLanguage`, `auto` follows the conversation. |
| `conversations.gap` | duration | `00:02:00` | `hh:mm:ss`, 30 seconds to 1 hour. |
| `audio.retentionDays` | int | `14` | 0 to 3650. |

API keys are environment only (open decision 6): `Nytka__Stt__ApiKey` and `Nytka__Llm__ApiKey`. The
table never holds one and no request writes one. `GET` lists them read-only, with `type: secret`,
`value: null`, `isSet` and `locked: true`, so the app can say whether a key is configured. A `PATCH`
value of `null` or an empty string removes a table row and restores the default.

## The AI layer

### When it runs

Every minute the scheduler queues `enrich-conversation` and sets `aiStatus: pending` for each
`closed` conversation that has `aiStatus: none` and ended within `Nytka__Llm__BackfillDays` (7); or
is `done` or `skipped` with a segment newer than the last run (`ai_through_segment_id`); or is
`failed` with fewer than three failed rounds and a last failure an hour old. Nothing is queued while
`llm.baseUrl` or `llm.model` is empty. `POST /conversations/{id}/enrich` queues one at once. The job
waits, a minute at a time, while a batch of its conversation is `pending`, and ends quietly when the
conversation is gone. An open conversation is never summarized.

### The call

`POST {llm.baseUrl}/chat/completions` with `Authorization: Bearer <key>` when `Nytka__Llm__ApiKey` is
set. The body holds `model`, a system and a user message, and `response_format` as a `json_schema` object
(`strict: true`, name `conversation`, the schema below); with `Nytka__Llm__JsonMode=object` it sends
`{ "type": "json_object" }` and puts the schema in the prompt. It sends no temperature and no token
limit, because some models refuse them.

The user message holds the conversation's date and its transcript, one line per segment:
`[HH:mm:ss] Label: text` in UTC, with no label when the segment has no speaker. The system message
(server code, not a setting) asks for `llm.outputLanguage` (`auto`: the conversation's own language),
for tasks only the wearer has to do, and warns that speaker labels may differ between parts. A
transcript over `Nytka__Llm__MaxInputChars` (100,000) is cut at segment boundaries into windows, each
answered with the same schema and merged by one last call; more than six windows fail the run (open
decision 3). Under 20 words the conversation is `skipped` ("Too short to summarize.") without a call.

```json
{ "type": "object", "additionalProperties": false, "required": ["title", "summary", "tasks"],
  "properties": { "title": { "type": "string" }, "summary": { "type": "string" },
                  "tasks": { "type": "array", "items": { "type": "string" } } } }
```

The server validates the answer itself, after stripping a surrounding Markdown code fence: not JSON,
a missing or extra property or a wrong type fails the attempt. Lengths are enforced by cutting: a
title at 80 characters, a summary at 1,200, a task at 200, ten tasks. The job makes up to three
attempts, 30 seconds and then 2 minutes apart; HTTP 429, 5xx, timeouts and bad answers all count.
After the last, `aiStatus` is `failed` and `aiMessage` gives one sentence, such as "The language
model endpoint answered 429." Messages and logs never hold transcript text or a response body.

### Result and re-runs

Every finished run stores `ai_status`, `ai_message` and `ai_updated_at`. A `done` or `skipped` run
also stores `ai_through_segment_id` (the highest segment id read before the call, so speech that
arrives during the call starts another run); a failed run adds one to `ai_failures`. A `done` run
also stores `ai_title` and `ai_summary`, clears `ai_failures`, reconciles the tasks and publishes
events, in one transaction.

Tasks reconcile per conversation by fingerprint: the AI text lower-cased, letters and digits only,
single spaces, never recomputed on edits. A returned task whose fingerprint has a row, in any state,
changes nothing; a new fingerprint inserts a task; an untouched row (open, not edited, not deleted)
that the model no longer returns is deleted. Rows you completed, edited or deleted stay, and a
deleted task stays as a tombstone (`deleted_at`) so it does not return. After each `done` run the
job publishes `conversation.ready` and `task.created` per inserted task; completing a task publishes
`task.completed`. v0.2 has no subscriber; v0.4 delivers them to webhooks (the Events seam below).

### Speaker labels

`TranscriptionClient` reads `segments[].speaker` (a string, or an integer taken as its decimal
string; trimmed; up to 64 characters; else null) into `segments.speaker`; the raw answer stays as
stored. Labels are stable across batches only when the provider names speakers, for instance through
voice enrollment. Nytka sends each batch on its own, so an anonymous `SPEAKER_00` can mean different
people in different batches, and v0.2 does not reconcile them.

Errors are problem details as in v0.1; a `400` about values adds `errors`, an object from key or
field to a list of messages (ASP.NET's validation problem). Objects always carry every field:

- **Conversation:** `{ id, startedAt, endedAt, status, preview, title, summary, aiStatus }`. `title`
  is the title you set, else the generated one; `title` and `summary` are null until the first run;
  `aiStatus` is `none`, `pending`, `done`, `skipped` or `failed`.
- **ConversationDetail:** the Conversation fields except `preview`, plus `titleEdited`, `aiMessage`,
  `aiUpdatedAt`, `tasks` (Tasks, deleted ones left out) and `segments`, each
  `{ id, startedAt, endedAt, text, speaker }`.
- **Setting:** `{ key, type, value, isSet, source, locked, default }`. `type` is `string`, `url`,
  `secret`, `duration`, `int`, `language` or `bool`; `value` is null for a secret; `source` is `env`,
  `db` or `default`; `locked` is true when `source` is `env`, and always for a secret. Values travel
  as strings, as an environment variable would carry them (`"14"`, `"true"`), or null.

## MCP

`POST /mcp` speaks MCP over Streamable HTTP through the official C# SDK, NuGet package
`ModelContextProtocol.AspNetCore` 2.x (revision 2026-07-28; older clients on 2025-11-25 and earlier
still work). It is stateless: no session, and `GET` and `DELETE` on `/mcp` answer `405`. The bearer
token needs scope `read` or `admin`. A request with an `Origin` header (a browser) gets `403`, the
guard against DNS rebinding. Every tool is read-only (`readOnlyHint: true`), declares an
`outputSchema` and returns its object as `structuredContent` and as JSON text. An unknown id is a
tool error (`isError: true`, "No such conversation."); bad arguments are JSON-RPC `-32602`.

| Tool | Input | Output |
|---|---|---|
| `list_conversations` | `since?`, `before?` (ISO 8601), `limit?` (1 to 50, default 20) | `{ items: [{ id, startedAt, endedAt, title, summary, preview }], nextBefore }` |
| `get_conversation` | `id` (UUID), `transcript?` (default true), `part?` (from 1, default 1) | `{ id, startedAt, endedAt, title, summary, tasks: [{ id, text, done }], transcript, truncated, part, parts }` |
| `list_tasks` | `status?` (`open` or `done`), `conversationId?`, `before?` (task id), `limit?` (1 to 200, default 50) | `{ items: [Task], nextBefore }` |

`transcript` holds the prompt's lines, cut at line boundaries into parts of at most 60,000
characters. `part` (from 1, default 1) picks one, and one outside `1` to `parts` is `-32602`;
`parts` counts them and `truncated` is true while a later part exists. Only the first 20 parts are
read. `transcript` is null when `transcript` is false. Fields and rules match REST.

## Data

`?` marks a nullable column; every other column is `not null`. Ids are UUID v7, so id order is
creation order.

| Table | Columns |

| `settings` (0003) | `key` text pk; `value` text; `updated_at` timestamptz. |
| `transcription_batches` (0004) | New column `finished_at` timestamptz?: when the batch reached `done` or `failed`, by the database clock; null while pending and for batches from before the migration. |

| `conversations` (0004) | New columns `title` text? (set by the user, wins over `ai_title`); `ai_title` text?; `ai_summary` text?; `ai_status` text (`none` by default, `pending`, `done`, `skipped`, `failed`); `ai_message` text?; `ai_updated_at` timestamptz?; `ai_through_segment_id` bigint? (the highest `segments.id` the last run read); `ai_failures` int, default 0. |

## Jobs and configuration

One new job: `enrich-conversation` (payload `{ conversationId, force }`, dedupe key
`enrich-conversation:{id}`), queued by the scheduler's scan or by `POST .../enrich`. It runs in the
`Ai` lane, apart from v0.1's four kinds (the `Audio` lane), so a slow model never delays
transcription. Every settings key is also its environment variable, and the admin token stays
required. Compose defaults every optional variable to empty (track E), so the server's own defaults
(2 minutes, 14 days) apply and the app can edit them. Environment only:

| Variable | Default | Meaning |
|---|---|---|
| `Nytka__Stt__ApiKey` | empty | Key for the transcription endpoint, as in v0.1. |
| `Nytka__Llm__ApiKey` | empty | Key for the model endpoint; empty for a local server. |
| `Nytka__Llm__JsonMode` | `schema` | `schema` or `object`, as in "The call". |
| `Nytka__Llm__TimeoutSeconds` | `120` | Per request. |
| `Nytka__Llm__MaxInputChars` | `100000` | Transcript size per window. |
| `Nytka__Llm__BackfillDays` | `7` | How far back unprocessed conversations are summarized. |

## App

Five tabs: Conversations, Tasks, Memories, Ask and Device; Memories and Ask show "Arrives in a later
version". Screens follow Material 3 with dynamic color; lists refresh by pulling down and have an
empty and an error state (Retry). A server that lacks an endpoint answers `404`, and the screen says
"This server needs an update".

- **Conversations tab.** A row shows the title (else the time range), two lines of summary (else the
  preview), and time range and length. A chip reads "Summarizing" while `aiStatus` is `pending` and
  "Summary failed" when it is `failed`.
- **Conversation screen.** Title in the top bar; a summary card; a tasks card whose checkboxes act as
  in the Tasks tab; the v0.1 transcript with the speaker's name in color above each run of segments
  by one speaker (six colors, by first appearance). Overflow: Rename (empty restores the generated
  title), Regenerate summary (disabled while the conversation is open), Delete, and in developer
  mode Raw transcription.
- **Tasks tab.** Open tasks newest first: checkbox, text, and the conversation's title and day. Tap
  opens the conversation; the row menu has Edit and Delete (with a confirmation). Done tasks sit
  below, collapsed, 30 at a time.
- **Developer mode, Server.** Server settings: the catalog grouped by key prefix, a field per `type`,
  locked keys read-only ("Set by the server's environment"), API keys as Set or Not set (read-only),
  and Save sending only changed keys and showing `errors` under their fields.
  Access tokens: name, scope, created, last used, revoked; Create shows the token once with Copy;
  Revoke asks first. The v0.1 server status line shows `lastError` with `lastErrorAt` only while
  `lastError` is set.

## Open decisions

Each item carries its status: decided or accepted by the owner, or open with a recommendation.

1. **AI job lane.** A slow model would stall transcription, so `enrich-conversation` gets its own
   lane. Accepted: yes.
2. **JSON mode.** `json_schema` first, `Nytka__Llm__JsonMode=object` for endpoints without it.
   Accepted: the knob only; an automatic fallback would double calls.
3. **Long transcripts.** Windows plus a merge call (six at most), or cutting the middle. Accepted:
   windows; a cut drops tasks without saying so.
4. **`read` on REST.** `read` tokens read conversations and tasks over REST too, not only MCP.
   Accepted: yes; agents and webhook receivers fetch details that way.
5. **Backfill and retry.** A seven-day backfill after an upgrade or once the model is configured,
   and hourly retries of failed runs (three rounds). Accepted: yes; an outage would leave holes.
6. **API keys.** Decided: they come only from the server environment, never from the database and
   never through the API; the app edits non-secret settings only.

callback that selects the Conversations tab and opens `conversation/{id}` in its NavHost, where that
route lives; the Tasks and Memories tabs and the search screen receive it); `app/ui/device/DeviceTab.kt`
and `app/ui/developer/DeveloperScreen.kt` (a Server section with three rows: Server settings,
Access tokens, Webhooks); `app/ui/conversations/ConversationsScreen.kt` (a `search` route and icon,
hidden while `SEARCH_ENABLED` is false); stub screens `app/ui/tasks/TasksTab.kt` and
`memories/MemoriesTab.kt` (each taking `onOpenConversation`), `ask/AskTab.kt`,
`search/SearchScreen.kt` (taking `onOpenConversation` and `onBack`; holds `SEARCH_ENABLED`) and
`developer/server/{ServerSettings,Tokens,Webhooks}Screen.kt`; `core/api/NytkaApi.kt` (`request`
becomes `internal`, so the other clients in `:core` can call it, takes a JSON body and maps `403`,
`409` and a `400` with `errors` to `Forbidden`, `Conflict` and `Invalid` failures) with the matching
types in `ApiModels.kt`; `app/src/test/.../ui/AppTabTest.kt`. Each area registers its client in its
own Hilt module (`app/di/<Area>Module.kt`), so `AppModule.kt` is never edited.

- **A.** Auth is one ASP.NET Core authentication handler plus one authorization requirement that
  reads the `AllowRead` metadata; `BearerTokenFilter` goes. A settings service resolves each key as
  the Settings section says, dropping empty environment values so they never shadow the table. It
  feeds `IOptionsMonitor<T>` and makes `IOptions<NytkaOptions>` a live view, so v0.1's handlers need
  no edit. The table loads in a hosted service, which starts after the migrator; before that,
  options come from the environment and the defaults. It never touches a secret key in the table.
- **B.** Registers `llm.*` as an `ISettingsGroup` (the API key read-only), builds on `TranscriptText`,
  `TranscriptWindows` and `LlmJson`, publishes the events, adds `AllowRead()` to the endpoints marked
  `read`, sets `transcription_batches.finished_at` in `BatchStore` and computes the `/status` fields.
- **C.** `AddNytkaMcp` is `AddMcpServer().WithHttpTransport()` with `WithToolsFromAssembly()`, so
  v0.4's tools register themselves. `MapNytkaMcp` is `MapMcp("/mcp").RequireNytkaAuth().AllowRead()`:
  the `/api/v1` group's auth does not cover `/mcp`. `McpQueries` is its own read-only SQL over the
  final schema, so C never waits for B's stores. Its tests assert its three tools by name, never a
  count. It merges after A: an MCP endpoint without token checks must never reach `main`.
- **D.** Opens conversations through S2's `onOpenConversation`, and meets the server only through the
  JSON in this spec (MockWebServer fixtures).
- **E.** Compose defaults every optional variable to empty (no `:-00:02:00`, no `:-14`) and
  `.env.example` lists them commented out; `CLAUDE.md`'s job invariant becomes "one job at a time per
  lane"; `docs/vision.md` gets its status line and loses the sentence that the app writes API keys,
  which now come only from the environment.
