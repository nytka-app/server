# Nytka v0.4: memory and search

**Status: draft.** The whole picture lives in [../vision.md](../vision.md); this spec builds on
[v0.2.md](v0.2.md) and takes its conventions, token scopes, error shape and seams as given.
Migration `0005` belongs to v0.3, so v0.4 uses `0006` to `0008`.

Version 0.4 gives the server a memory and a search. The language model extracts lasting facts about
you from your conversations, one full-text search covers transcripts, titles, summaries and memories
in Ukrainian and English together, and outgoing webhooks tell your other tools when something new
exists. This spec covers both repositories, `nytka-app/android` and `nytka-app/server`. Everything
adds to `/api/v1`, and `apiVersion` stays `1`.

## Done when

1. After a conversation is summarized, up to five memories are extracted from it (a fake model in
   the tests), with `source: ai` and the conversation's id. A fact already known, even one you
   deleted, is not added again; an edited memory is never rewritten by extraction.
2. Memories can be listed, added, edited and deleted over the API and in the Memories tab. Deleting
   a conversation deletes its memories. `memories.enabled` off, or no model, means no extraction.
3. Search works across both languages: `kyiv` finds "Kyiv"; `розмова` finds "розмови" and "Розмова";
   `running` finds "run"; a query mixing both scripts finds a conversation that has both.
4. Search returns one hit per conversation and per memory, ranks title above summary and memory above
   transcript, hides deleted items, and wraps matches in `<mark>`. Among 100,000 segments a search
   whose terms match up to 5,000 of them answers in under 300 ms, on the Compose image
   (`postgres:17-alpine`).
5. A webhook's secret shows once. A receiver that recomputes the signature gets the header's value. A
   failing receiver sees retries after 1 minute, 5 minutes, 30 minutes, 2 hours and 12 hours (fake
   clock) and the delivery ends `failed`; a `2xx` stops them. `test` delivers a `ping`.
6. A summary delivers `conversation.ready` and one `task.created` per new task, completing a task
   delivers `task.completed`, a new memory `memory.created`: once per active matching webhook, in the
   transaction of the change. A delivery keeps no payload once it is `delivered` or `failed`.
7. MCP lists exactly five tools (v0.2's three, `search` and `list_memories`); each returns what REST
   returns.
8. A v0.2 database migrates, and search finds text from before the upgrade.
9. On a phone: the Memories tab adds, edits and deletes; search opens a conversation from a hit;
   developer mode creates a webhook, shows its secret once, sends a test and lists deliveries.
10. CI is green in both repositories, and the docs cover every new endpoint, variable and tool.

## Scope

**In:** memories (extraction, API, tab, MCP tool); full-text search (API, app, MCP tool); webhooks
(events, signature, retries, delivery log, API, app).

**Out:** questions about your history (the Ask tab); vector search; searching tasks; memory
categories; extraction over conversations summarized before the upgrade (regenerate a summary to
feed one in); redelivery of failed webhooks; other event types; payloads with transcripts; secret
rotation (delete the webhook and create it again); matching anonymous speaker labels.

## Memories

**Extraction.** Each `conversation.ready` event (every stored summary, first or re-run) makes a
subscriber queue `extract-memories` (recording `memory_runs.status: pending`), when
`memories.enabled` (default true) is on and the model is configured. The job ends quietly when the
conversation is gone or `memory_runs.through_segment_id` already covers its last segment. It sends
the title, the transcript (windowed as in v0.2; the
candidates of all windows are pooled), the newest 200 memories as `id: text` lines, and
`memories.userName`, which says who "you" is (empty: the person wearing the pendant). The system
message asks for durable facts about you (who you are, family, friends, home, work, health, habits,
preferences, goals, commitments), never one-off events, tasks or other people's affairs, in
`llm.outputLanguage`. Call, validation and attempts are as in v0.2, with this schema; text is cut at
300 characters, at most five memories are kept, and `replaces` names a listed memory:

```json
{ "type": "object", "additionalProperties": false, "required": ["memories"],
  "properties": { "memories": { "type": "array", "items": { "type": "object",
    "additionalProperties": false, "required": ["text", "replaces"],
    "properties": { "text": { "type": "string" }, "replaces": { "type": ["string", "null"] } } } } } }
```

**Apply**, in one transaction. A candidate whose fingerprint (the v0.2 rule) matches any row, deleted
ones included, is dropped. One whose `replaces` names a live, unedited memory rewrites it (text,
fingerprint, source conversation, `updated_at`). Any other inserts a row with `source: ai` and
publishes `memory.created`. `memory_runs` then records `done` and the highest segment id read; after
three failed attempts it records `failed`, and the job is queued again an hour later, three rounds
at most.

**Rules.** Editing sets `edited` and keeps the fingerprint; extraction never rewrites an edited or
hand-made memory. Deleting leaves a tombstone (`deleted_at`) so the fact does not return; adding the
same text by hand revives it. A conversation's memories go with it (open decision 2).

## Search

**The configuration.** PostgreSQL ships Snowball stemmers for English and Russian but none for
Ukrainian, and a Hunspell dictionary needs files installed in the image. Migration 0007 therefore
builds a text search configuration from stock parts, which works on the plain `postgres:17-alpine`
image with no extension:

```sql
create text search configuration nytka (copy = pg_catalog.simple);
alter text search configuration nytka alter mapping for asciiword, asciihword, hword_asciipart with english_stem;
alter text search configuration nytka alter mapping for word, hword, hword_part with russian_stem;
```

ASCII words are stemmed as English, every other word (Cyrillic, accented Latin) as Russian, all
other token types stay `simple`. Ukrainian shares most case endings with Russian, so many forms
collapse to one stem, and prefix matching covers the rest. Rejected: `simple` alone (no stemming, so
every inflection misses), Hunspell `uk_UA` (files in the image) and `pg_trgm` (a larger index,
substring noise, weak ranking). Cyrillic case folding depends on the database's `LC_CTYPE`, so a
test runs on the Compose image. Changing the configuration later means rewriting the generated
columns and reindexing.

**Index.** Generated, stored `tsvector` columns with GIN indexes: `segments.search` over `text`;
`conversations.search` over the title (the one you set, else the generated one) in weight A and the
summary in weight B; `memories.search` over `text` in weight B. The code that writes those rows does
not change.

**Query.** `q` is cut into terms of letters and digits (the first eight); every term must match and
matches as a prefix (`to_tsquery('nytka', 'term:*')` joined with `&`); no term is a `400`. A hit is
one conversation (its best source: title, summary or a segment) or one memory, highest `score`
first. `score` is `ts_rank_cd` with its default weights: title 1.0, summary and memory 0.4,
transcript 0.1. `snippet`
is `ts_headline` (one fragment of 8 to 25 words, matches in `<mark>`) of the best segment, else the
summary, else the memory text; apart from the `<mark>` tags it is plain, unescaped text.

## Webhooks

**Events.** `conversation.ready` (a summary was stored), `task.created`, `task.completed`,
`memory.created`, and `ping` (only from the test call). A webhook lists the events it wants, or `*`.
The event subscriber writes delivery rows inside the transaction of the change, so a delivery exists
exactly when the change committed; a webhook gets nothing for events from before it existed, or
while it is inactive.

**Payload.** JSON `{ id, type, createdAt, data }`, `id` the event's UUID. `data` is, for
`conversation.ready`, `{ id, startedAt, endedAt, title, summary, tasks: [{ id, text }] }` (deleted
tasks left out); for `task.created` and `task.completed`, the Task; for `memory.created`,
`{ id, text, conversationId }`; for `ping`, `{}`. A payload never carries a transcript: a receiver
that needs one fetches it with a `read` token.

**Signature.** Headers `Content-Type: application/json`, `Nytka-Event` (the type), `Nytka-Delivery`
(the delivery id), `Nytka-Timestamp` (Unix seconds) and `Nytka-Signature: v1=<hex>`: the HMAC-SHA256,
in lowercase hex, of `"{timestamp}.{body}"` (the exact bytes sent) with the webhook's secret (its
UTF-8 bytes) as key. Receivers should refuse timestamps more than five minutes old and can drop
repeats by event `id`: delivery is at least once and not ordered. A secret is `whsec_` plus 43
base64url characters; it sits in the table as plain text, since it signs, and is shown once.

**Delivery.** One `deliver-webhook` job per delivery, lane `Hooks`: POST, 10 seconds, no redirects,
`2xx` succeeds. Any other outcome retries after 1 minute, 5 minutes, 30 minutes, 2 hours and 12
hours (six attempts in all), then the delivery is `failed`; the handler counts attempts itself and
reschedules with `JobOutcome.RunAgain`. The log keeps `status`, `attempts`, `last_status_code` and a
short `last_error` ("HTTP 500", "timeout", "connection refused"), never a response body, and drops a
payload once its delivery ends. The newest 200 deliveries per webhook are kept. A URL is `http` or
`https`, at most 2,048 characters; private addresses are allowed. At most 20 webhooks.

## HTTP API v1

| Method | Path | Scope | Result |
|---|---|---|---|
| GET | `/api/v1/memories?before=&limit=` | read | `{ items: [Memory], nextBefore }`, newest first, where Memory is `{ id, text, source, conversationId, createdAt, updatedAt }` (`source` is `ai` or `user`; `conversationId` may be null). `limit` defaults to 50, caps at 200; `before` is a memory id. |
| POST | `/api/v1/memories` | admin | Body `{ text }`, 1 to 300 characters. 201 with the Memory (`source: user`); 400; 409 when a live memory already holds the fact. |
| PATCH | `/api/v1/memories/{id}` | admin | Body `{ text }`. 200 with the Memory; 400; 404. |
| DELETE | `/api/v1/memories/{id}` | admin | 204; 404. |
| GET | `/api/v1/search?q=&kinds=&limit=&offset=` | read | `{ items: [Hit], nextOffset }`. `kinds` is a comma list of `conversation` and `memory` (default both); `limit` defaults to 20, caps at 50; `offset` runs 0 to 500; `nextOffset` is null on the last page. 400 for no term or an unknown kind. Hit: `{ kind, id, score, title, snippet, at, conversationId }`; `title` is null for a memory; `at` is a conversation's `startedAt` or a memory's `updatedAt`; `conversationId` is set only for a memory with a source. |
| POST | `/api/v1/webhooks` | admin | Body `{ url, events, description? }`, `events` naming event types or `*` (`ping` is not one). 201 with the Webhook and `secret`; 400; 409 at 20 webhooks. |
| GET | `/api/v1/webhooks` | admin | `{ items: [Webhook] }`, where Webhook is `{ id, url, events, description, active, createdAt, lastDelivery }` and `lastDelivery` is `{ status, at }` or null. |
| PATCH | `/api/v1/webhooks/{id}` | admin | Body with any of `url`, `events`, `description`, `active`. 200 with the Webhook; 400; 404. |
| DELETE | `/api/v1/webhooks/{id}` | admin | 204; 404. Its deliveries go with it. |
| POST | `/api/v1/webhooks/{id}/test` | admin | Queues a `ping`, even while the webhook is inactive. `202 { deliveryId }`; 404. |
| GET | `/api/v1/webhooks/{id}/deliveries?limit=` | admin | `{ items: [Delivery] }`, newest first (`limit` defaults to 30, caps at 100), where Delivery is `{ id, eventType, status, attempts, lastStatusCode, lastError, createdAt, deliveredAt }`. 404. |

Search ranks by relevance, so it pages with `offset` instead of v0.1's `before`. Errors, `401` and
`403` are as in v0.2.

## Data

`?` marks a nullable column; every other column is `not null`. Ids are UUID v7.

| Table | Columns |
|---|---|
| `memories` (0006) | `id` uuid pk; `text` text; `fingerprint` text unique (of the text as created or last rewritten by extraction; a tombstone keeps its row); `source` text (`ai` or `user`); `conversation_id` uuid?, references `conversations` on delete cascade; `edited` boolean, default false; `deleted_at` timestamptz?; `created_at` and `updated_at` timestamptz. |
| `memory_runs` (0006) | `conversation_id` uuid pk, references `conversations` on delete cascade; `status` text (`pending`, `done`, `failed`); `through_segment_id` bigint?; `failures` int, default 0; `message` text?; `updated_at` timestamptz. |
| search (0007) | The configuration `nytka` above; a `search` tsvector column, generated and stored, with a GIN index, on `segments` (`to_tsvector('nytka', text)`), on `conversations` (`setweight` A on `coalesce(title, ai_title, '')`, B on `ai_summary`) and on `memories` (`text`, weight B). |
| `webhooks` (0008) | `id` uuid pk; `url` text; `secret` text; `events` text[]; `description` text?; `active` boolean, default true; `created_at` and `updated_at` timestamptz. |
| `webhook_deliveries` (0008) | `id` uuid pk; `webhook_id` uuid, references `webhooks` on delete cascade; `event_id` uuid; `event_type` text; `payload` jsonb? (only until the delivery ends); `status` text (`pending`, `delivered`, `failed`); `attempts` int, default 0; `last_status_code` int?; `last_error` text?; `created_at` timestamptz; `delivered_at` timestamptz?. Index on (`webhook_id`, `created_at` desc). |

## Jobs and configuration

| Kind | Lane | Payload | Dedupe key | Runs |
|---|---|---|---|---|
| `extract-memories` | `Ai` | `{ conversationId }` | `extract-memories:{id}` | Queued by the memory subscriber on `conversation.ready`. |
| `deliver-webhook` | `Hooks` | `{ deliveryId }` | `deliver-webhook:{deliveryId}` | Queued in the event's transaction; rescheduled for each retry. |

Two settings join the catalog (each is also its environment variable): `memories.enabled` (bool,
default `true`, `Nytka__Memories__Enabled`) and `memories.userName` (string, up to 64 characters,
default empty, `Nytka__Memories__UserName`). Nothing else is configurable.

## App

The Memories tab replaces its placeholder; the search icon on the Conversations tab and a Webhooks
row in developer mode come to life. A server without the endpoints answers `404`, and the screens
say "This server needs an update".

- **Memories tab.** Newest first: the text, and the source conversation's title and day when there
  is one (tap opens it). The row menu has Edit and Delete (confirmed); Add opens a one-field dialog.
  The empty state says what memories are and that they come from summarized conversations.
- **Search.** A text field that searches as you type (after 300 ms, one letter or digit at least),
  filter chips All, Conversations and Memories, and hit rows: the title or the memory text, the
  snippet with the `<mark>` parts in bold, and the date. A conversation hit opens the conversation;
  a memory hit opens its source conversation when it has one.
- **Developer mode, Webhooks.** A list (URL, events, an active switch, the last delivery's status).
  Add takes a URL, event checkboxes and a description, then shows the secret once with Copy. A
  webhook's screen has Send test, its deliveries (status, attempts, HTTP status or error, time) and
  Delete (confirmed).

## Open decisions

Each has a recommendation, which the tracks follow unless you overrule it at approval.

1. **Search configuration.** `nytka`: English stems for ASCII words, Russian stems for the rest,
   prefix matching. Not yet run against a database: Done when 3 and 4 are its test. Recommendation:
   ship it if they pass; add a Ukrainian Hunspell dictionary later if recall proves poor.
2. **Memories and conversation deletion.** Deleting a conversation deletes the memories taken from
   it. Recommendation: yes; a derived fact would otherwise outlive the record you deleted.
3. **Who "you" is.** An optional `memories.userName` names you for the model. Recommendation: yes;
   without it facts about other speakers leak in.
4. **Webhook payloads.** They omit transcripts. Recommendation: omit; receivers fetch what they need
   with a `read` token.
5. **Webhook secrets.** Plain text in the table (they sign), shown once, no rotation. Recommendation:
   yes.
6. **Prefix matching.** Every query term also matches as a prefix. Recommendation: yes; it absorbs
   Ukrainian endings the stemmer misses, at the cost of some noise on short terms.
