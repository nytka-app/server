# Nytka v0.4: memory and search

**Status: draft.** The whole picture lives in [../vision.md](../vision.md); this spec builds on
[v0.2.md](v0.2.md) and takes its conventions, token scopes, settings rules, error shape and seams as
given. Migration `0005` belongs to v0.3, so v0.4 uses `0006` to `0008`.

Version 0.4 gives the server a memory and a search. The language model extracts lasting facts about
you from your conversations, one full-text search covers transcripts, titles, summaries and memories
in Ukrainian and English together, and outgoing webhooks tell your other tools when something new
exists. This spec covers both repositories, `nytka-app/android` and `nytka-app/server`. Everything
adds to `/api/v1`, and `apiVersion` stays `1`.

## Done when

1. After a conversation is summarized, up to five memories are extracted from it (a fake model in
   the tests), with `source: ai` and the conversation's id. A fact already known, even one you
   deleted, is not added again; an edited memory is never rewritten by extraction. A run that fails
   its three attempts is tried again an hour later, three rounds at most.
2. Memories can be listed, added, edited and deleted over the API and in the Memories tab, each with
   its source conversation's title and day. Deleting a conversation deletes its memories.
   `memories.enabled` off, or no model, means no extraction.
3. With the Ukrainian dictionary installed and `search.dictionary` set to `uk_hunspell`, `зустріч` finds "зустрічі" and "зустрічами", `рік` finds
   "року" and "роки" (prefix matching alone cannot); `running` finds "run";
   `kyiv` finds "Kyiv"; a query mixing both scripts finds a conversation that has both; and
   `ts_lexize('nytka_uk', 'зустрічами')` includes `зустріч`.
4. By default (`search.dictionary = simple`) migration 0007 applies with or without the files, and
   Cyrillic words match exactly or by prefix: `зустріч` still finds "зустрічами", `рік` does not find
   "року". Asking for `uk_hunspell` without the files warns, in the database log and in the server's log,
   and stays on `simple`. With the files mounted, setting `uk_hunspell` switches to the dictionary and
   re-indexes in the background, and the queries of item 3 pass; setting `simple` again, or removing the
   files, falls back and segment inserts keep working.
5. Search returns one hit per conversation and per memory, ranks title above summary and memory
   above transcript, hides deleted items, and wraps matches in `<mark>`. Among 100,000 segments a
   search whose terms match up to 5,000 of them answers in under 300 ms, on the Compose image
   (`postgres:17-alpine`) with the dictionary mounted. The dictionary's load time and its memory per
   session are measured there and recorded in the PR.
6. A webhook's secret shows once. A receiver that recomputes the signature gets the header's value. A
   failing receiver sees retries after 1 minute, 5 minutes, 30 minutes, 2 hours and 12 hours (fake
   clock) and the delivery ends `failed`; a `2xx` stops them. `test` delivers a `ping`.
7. A summary delivers `conversation.ready` and one `task.created` per new task, completing a task
   delivers `task.completed`, a new memory `memory.created`: once per active matching webhook, in the
   transaction of the change. A delivery keeps no payload once it is `delivered` or `failed`.
8. Each track's tests assert its own MCP tool by name; G's test asserts the full list, exactly five
   tools (v0.2's three, `list_memories` and `search`); each tool returns what REST returns.
9. A v0.2 database migrates, with or without the files, and search finds text from before the
   upgrade.
10. On a phone: the Memories tab adds, edits and deletes; search opens a conversation from a hit;
    developer mode creates a webhook, shows its secret once, sends a test and lists deliveries.
11. CI is green in both repositories and runs the dictionary tests, having fetched the files. The
    docs cover every new endpoint, variable and tool, and show how to fetch and mount the dictionary.

## Scope

**In:** memories (extraction, API, tab, MCP tool); full-text search (API, app, MCP tool, the
Ukrainian dictionary); webhooks (events, signature, retries, delivery log, API, app).

**Out:** questions about your history (the Ask tab); vector search; searching tasks; memory
categories; extraction over conversations summarized before the upgrade (regenerate a summary to
feed one in); redelivery of failed webhooks; other event types; payloads with transcripts; secret
rotation (delete the webhook and create it again); matching anonymous speaker labels.

## Memories

**Extraction.** Each `conversation.ready` event (every stored summary, first or re-run) makes a
subscriber queue `extract-memories` (recording `memory_runs.status: pending`), when
`memories.enabled` (default true) is on and the model is configured. The job ends quietly when the
conversation is gone or `memory_runs.through_segment_id` already covers its last segment. It sends
the title, the transcript (cut into windows with v0.2's `TranscriptWindows`; the candidates of all
windows are pooled), the newest 200 memories as `id: text` lines, and `memories.userName`, which
says who "you" is (empty: the person wearing the pendant). The system message asks for durable facts
about you (who you are, family, friends, home, work, health, habits, preferences, goals,
commitments), never one-off events, tasks or other people's affairs, in `llm.outputLanguage`. The
call, the `LlmJson` validation and the three attempts are as in v0.2, with this schema; text is cut
at 300 characters, at most five memories are kept, and `replaces` names a listed memory:

```json
{ "type": "object", "additionalProperties": false, "required": ["memories"],
  "properties": { "memories": { "type": "array", "items": { "type": "object",
    "additionalProperties": false, "required": ["text", "replaces"],
    "properties": { "text": { "type": "string" }, "replaces": { "type": ["string", "null"] } } } } } }
```

**Apply**, in one transaction. A candidate whose fingerprint (the v0.2 rule) matches any row, deleted
ones included, is dropped. One whose `replaces` names a live, unedited memory rewrites it (text,
fingerprint, source conversation, `updated_at`). Any other inserts a row with `source: ai` and
publishes `memory.created`. `memory_runs` then records `done` and the highest segment id read.

**Retries.** On its third attempt (`job.Attempts` equals `JobRunner.MaxAttempts`) the handler catches
the failure, records `failed` and adds one to `memory_runs.failures`, and returns
`JobOutcome.RunAgain(1 hour)` while `failures` is under three, `Done` after that. `OnGiveUpAsync`
cannot re-queue the job: it still holds its dedupe key, and the runner deletes it right after.

**Rules.** Editing sets `edited` and keeps the fingerprint; extraction never rewrites an edited or
hand-made memory. Deleting leaves a tombstone (`deleted_at`) so the fact does not return; adding the
same text by hand revives it. A conversation's memories go with it (open decision 2).

## Search

**The configuration.** Decided: the dictionary is opt-in. The default configuration sends ASCII words
through `english_stem` and Cyrillic words through `simple`, and every query term also matches as a
prefix. The setting `search.dictionary` (`simple`, the default, or `uk_hunspell`; a non-secret catalog
key, environment variable `Nytka__Search__Dictionary`) puts a Ukrainian Hunspell dictionary in front of
`simple` for Cyrillic words, used only when its files load. A Hunspell dictionary maps each word form it
knows to its base forms and passes unknown words (names, slang) on to `simple`, so `зустріч` finds
"зустрічі" and "зустрічами", and `рік` finds "року", which prefix matching alone cannot. When the
dictionary is asked for and loads, `nytka_search_setup('uk_hunspell')` runs this:

```sql
create text search dictionary nytka_uk (template = ispell, dictfile = uk_ua, afffile = uk_ua);
create text search configuration nytka (copy = pg_catalog.simple);
alter text search configuration nytka
    alter mapping for asciiword, asciihword, hword_asciipart with english_stem;
alter text search configuration nytka
    alter mapping for word, hword, hword_part with nytka_uk, simple;
```

**The dictionary.** The Hunspell package of the dict_uk project (Andriy Rysin): the release asset
`hunspell-uk_UA_<version>.zip` (v6.8.6 of 2026-09-19 was the latest, about 1.6 MB), holding
`uk_UA.aff` and `uk_UA.dic` (the fetch script checks that they are there). LibreOffice ships the same
dictionary as its `uk_UA` package. **Licence, unresolved; opt-in for that reason.** The package's own README says GPL 3.0 or
above, LGPL 2.1 or above and MPL 1.1 (its `README.md` says MPL 1.1); the project README says the
dictionary *data* are CC BY-NC-SA 4.0 (non-commercial, share-alike), the software GPL 3.0 or above,
and that the derivative projects have their own licences. `uk_UA.dic` is generated from that data, and
upstream does not say how the two fit. So Nytka never commits, bundles or redistributes the files: the
script downloads them at deploy time onto the operator's machine, the licence notice travels with them,
and `NOTICE` says so. Personal self-hosting is fine either way; commercial use or redistribution
needs the upstream authors' answer. This is a reading, not legal advice. If Postgres rejects a
directive in the current `.aff`, the script drops that directive on the user's machine (the `.dic` is
never edited); v6.8.6 loads as is on Postgres 17.11.

**The files.** Postgres wants two files in `$SHAREDIR/tsearch_data`: `uk_ua.dict` and `uk_ua.affix`,
which are `uk_UA.dic` and `uk_UA.aff` renamed, in UTF-8, with a lowercase base name and no `.stop`
file. In `postgres:17-alpine`, `$SHAREDIR` is `/usr/local/share/postgresql` (its Dockerfile
configures `--prefix=/usr/local`); the Debian images use `/usr/share/postgresql/17`. Any server
answers `pg_config --sharedir`.

**Delivery** (open decision 7). Recommended: the stock `postgres:17-alpine` with `./tsearch_data/`
mounted read-only as a directory, filled once by `scripts/fetch-uk-dictionary.sh --accept-licence` (it prints the licence caveat and refuses to run
without the flag; a pinned release URL and SHA-256, unzip, rename, UTF-8 check). The mount is optional: `docker-compose.yml` starts
Postgres through a small entrypoint that links `uk_ua.dict` and `uk_ua.affix` into `tsearch_data` when
they exist, so missing files never stop Postgres and search falls back to `simple`. The repository and
the images carry no dictionary. The alternative is a small custom image built by CI (`FROM
postgres:17-alpine` plus the files): users skip the script, but the project then redistributes the
files (see the licence above) and patches a second image.

**The fallback.** Migration 0007 must not fail without the files (an external Postgres). It defines
`nytka_search_setup()` and calls it once. The function loads `nytka_uk` with `ts_lexize`, creating it
first when it does not exist. If that works it maps Cyrillic words to `nytka_uk, simple`; if not it
maps them to `simple`, drops the dictionary and raises a WARNING ("Ukrainian dictionary not loaded:
...; Cyrillic words match exactly"). Whenever the mapping changes it clears every `search` vector, since
each was made under the old mapping, and the indexer (below) makes them again. The server calls the
function at every start, whenever the setting changes, and again whenever indexing or a query fails, in the background
(`SearchDictionarySync`), and logs what it found, so the configuration follows the setting and the files: set
later, it switches to the dictionary; files removed later, it falls back instead of failing. Only the
indexer and the queries ever evaluate the configuration; a write never does, so a missing or broken
dictionary can never fail an insert. `select nytka_search_setup();` runs it by hand.

**The cost.** Postgres reads a dictionary file once per session, on first use, about 65 MB and 2 to 3
seconds each. The indexer and the queries therefore share one pool of their own (`SearchStore`,
`Maximum Pool Size=2`, idle and connection lifetimes of a day), and no other connection touches the
configuration, so the dictionary costs two sessions and not one per pooled connection. G measures the
load time and the memory per session on the Compose image and records both in the PR. Cyrillic case
folding depends on the database's `LC_CTYPE`, so the tests run on that image. Rejected: the Russian
stemmer (wrong stems for Ukrainian words), `simple` alone (kept only as the fallback) and `pg_trgm` (a
larger index, substring noise, weak ranking).

**Index.** Plain nullable `tsvector` columns with GIN indexes: `segments.search` over `text`;
`conversations.search` over the title (the one you set, else the generated one) in weight A and the
summary in weight B; `memories.search` over `text` in weight B. A null vector means "not indexed
yet". `SearchDictionarySync` also runs the indexer: it fills vectors in batches of 500 by id, lowest
first, and polls every two seconds when caught up. A trigger clears the vector of a conversation whose
title or summary changed and of a memory whose text changed, so it is indexed again. The code that
writes those rows does not change. **Lag:** a new segment, summary or memory is searchable a few
seconds after it is written (longer while a large archive is indexed for the first time or after the
mapping changes); rows not yet indexed are simply not found.

**Query.** `q` is cut into terms of letters and digits (the first eight); every term must match and
matches as a prefix (`to_tsquery('nytka', 'term:*')` joined with `&`); no term is a `400`. A hit is
one conversation (its best source: title, summary or a segment) or one memory, highest `score`
first. `score` is `ts_rank_cd` with its default weights: title 1.0, summary and memory 0.4,
transcript 0.1. `snippet` is `ts_headline` (one fragment of 8 to 25 words) of the best segment, else the summary,
else the memory text, HTML-escaped by the server, with the matches wrapped in `<mark>`: the only
tag it holds.

## Webhooks

**Events.** `conversation.ready` (a summary was stored), `task.created`, `task.completed`,
`memory.created`, and `ping` (only from the test call). A webhook lists the events it wants, or `*`.
The event subscriber writes delivery rows inside the transaction of the change, so a delivery exists
exactly when the change committed; a webhook gets nothing for events from before it existed, or
while it is inactive.

**Payload.** JSON `{ id, type, createdAt, data }`, `id` the event's UUID. `data` is, for
`conversation.ready`, `{ id, startedAt, endedAt, title, summary, tasks: [{ id, text }] }` (deleted
tasks left out); for `task.created` and `task.completed`, the Task; for `memory.created`,
`{ id, text, conversationId }`; for `ping`, `{}`. A payload never carries a transcript: a receiver
that needs one fetches it with a `read` token.

**Signature.** Headers `Content-Type: application/json`, `Nytka-Event` (the type), `Nytka-Delivery`
(the delivery id), `Nytka-Timestamp` (Unix seconds) and `Nytka-Signature: v1=<hex>`: the HMAC-SHA256,
in lowercase hex, of `"{timestamp}.{body}"` (the exact bytes sent) with the webhook's secret (its
UTF-8 bytes) as key. Receivers should refuse timestamps more than five minutes old and can drop
repeats by event `id`: delivery is at least once and not ordered. A secret is `whsec_` plus 43
base64url characters; it sits in the table as plain text, since it signs, and is shown once.

**Delivery.** One `deliver-webhook` job per delivery, lane `Hooks`: POST, 10 seconds, no redirects,
`2xx` succeeds. Any other outcome retries after 1 minute, 5 minutes, 30 minutes, 2 hours and 12
hours (six attempts in all), then the delivery is `failed`; the handler counts attempts itself and
reschedules with `JobOutcome.RunAgain`. The log keeps `status`, `attempts`, `last_status_code` and a
short `last_error` ("HTTP 500", "timeout", "connection refused"), never a response body, and drops a
payload once its delivery ends. The newest 200 deliveries per webhook are kept. A URL is `http` or
`https`, at most 2,048 characters; private addresses are allowed. At most 20 webhooks.

## HTTP API v1

| Method | Path | Scope | Result |
|---|---|---|---|
| GET | `/api/v1/memories?before=&limit=` | read | `{ items: [Memory], nextBefore }`, newest first, where Memory is `{ id, text, source, conversationId, conversationTitle, conversationStartedAt, createdAt, updatedAt }` (`source` is `ai` or `user`; the three `conversation*` fields are null for a memory with no source). `limit` defaults to 50, caps at 200; `before` is a memory id. |
| POST | `/api/v1/memories` | admin | Body `{ text }`, 1 to 300 characters. 201 with the Memory (`source: user`); 400; 409 when a live memory already holds the fact. |
| PATCH | `/api/v1/memories/{id}` | admin | Body `{ text }`. 200 with the Memory; 400; 404. |
| DELETE | `/api/v1/memories/{id}` | admin | 204; 404. |
| GET | `/api/v1/search?q=&kinds=&limit=&offset=` | read | `{ items: [Hit], nextOffset }`. `kinds` is a comma list of `conversation` and `memory` (default both); `limit` defaults to 20, caps at 50; `offset` runs 0 to 500; `nextOffset` is null on the last page. 400 for no term or an unknown kind. Hit: `{ kind, id, score, title, snippet, at, conversationId }`; `title` is null for a memory; `at` is a conversation's `startedAt` or a memory's `updatedAt`; `conversationId` is set only for a memory with a source. |
| POST | `/api/v1/webhooks` | admin | Body `{ url, events, description? }`, `events` naming event types or `*` (`ping` is not one). 201 with the Webhook and `secret`; 400; 409 at 20 webhooks. |

| DELETE | `/api/v1/webhooks/{id}` | admin | 204; 404. Its deliveries go with it. |
| POST | `/api/v1/webhooks/{id}/test` | admin | Queues a `ping`, even while the webhook is inactive. `202 { deliveryId }`; 404. |

Search ranks by relevance, so it pages with `offset` instead of v0.1's `before`. Errors, `401` and
`403` are as in v0.2.

## Jobs and configuration

| Kind | Lane | Payload | Dedupe key | Runs |
|---|---|---|---|---|
| `extract-memories` | `Ai` | `{ conversationId }` | `extract-memories:{id}` | Queued by the memory subscriber on `conversation.ready`; see Retries. |
| `deliver-webhook` | `Hooks` | `{ deliveryId }` | `deliver-webhook:{deliveryId}` | Queued in the event's transaction; rescheduled for each retry. |

Three settings join the catalog (each is also its environment variable): `search.dictionary` (`simple` or
`uk_hunspell`, default `simple`, `Nytka__Search__Dictionary`; changing it re-indexes in the background), `memories.enabled` (bool,
default `true`, `Nytka__Memories__Enabled`) and `memories.userName` (string, up to 64 characters,
default empty, `Nytka__Memories__UserName`). Postgres finds the dictionary files by name.
Nothing else is configurable.

## App

The Memories tab replaces its placeholder; the search icon on the Conversations tab and a Webhooks
row in developer mode come to life. A server without the endpoints answers `404`, and the screens
say "This server needs an update".

- **Memories tab.** Newest first: the text, and the source conversation's title and day when there
  is one (tap opens it through S2's `onOpenConversation`). The row menu has Edit and Delete
  (confirmed); Add opens a one-field dialog. The empty state says what memories are and that they
  come from summarized conversations.
- **Search.** A text field that searches as you type (after 300 ms, one letter or digit at least),
  filter chips All, Conversations and Memories, and hit rows: the title or the memory text, the
  snippet with the `<mark>` parts in bold, and the date. A hit opens its conversation (a memory hit
  only when it has a source).
- **Developer mode, Webhooks.** A list (URL, events, an active switch, the last delivery's status).
  Add takes a URL, event checkboxes and a description, then shows the secret once with Copy. A
  webhook's screen has Send test, its deliveries (status, attempts, HTTP status or error, time) and
  Delete (confirmed).

## Open decisions

Each item carries its status: decided or accepted by the owner, or open with a recommendation.

1. **Search dictionary.** Decided: Cyrillic words through a Ukrainian Hunspell dictionary (dict_uk,
   MPL 1.1), then `simple`; ASCII words through `english_stem`.
2. **Memories and conversation deletion.** Deleting a conversation deletes the memories taken from
   it. Accepted: yes; a derived fact would otherwise outlive the record you deleted.
3. **Who "you" is.** An optional `memories.userName` names you for the model. Accepted: yes;
   without it facts about other speakers leak in.
4. **Webhook payloads.** They omit transcripts. Accepted: receivers fetch what they need with a
   `read` token.
5. **Webhook secrets.** Plain text in the table (they sign), shown once, no rotation. Accepted: yes.
   Unlike provider API keys, which v0.2 keeps in the environment, a webhook secret is made at run
   time and must be stored to sign.
6. **Prefix matching.** Every query term also matches as a prefix. Accepted: yes; it absorbs endings
   the dictionary misses, at the cost of some noise on short terms.
7. **Dictionary delivery.** The stock image with the files mounted from `./tsearch_data/`, or a
   small custom image. Open. Recommendation: the stock image and mounts; the project then ships no
   MPL files and patches no second image, at the price of one command before `docker compose up`.

  Testcontainers Postgres and skip with a message when `tsearch_data/` is empty; CI runs the script
  first. The shared fixture has no files, so it covers the fallback. G owns the full-list MCP test,
  which is why it merges last of the tool tracks.

  its own SQL and writes the delivery rows and jobs inside the event's transaction. Its tests publish
  events straight through `IEventPublisher`.
