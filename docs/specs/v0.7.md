# Nytka v0.7 (Omi is gone): my Omi history lives in Nytka

Omi's "Export All Data" file goes into Nytka once, so the conversations, memories and tasks from
before Nytka sit next to the new ones: listed, searchable, askable. After that the Omi app and its
cloud can go.

## Done when

1. `POST /api/v1/import/omi` with an Omi export file creates one conversation per kept Omi
   conversation, with its segments, title and summary, and answers with the counts. One that overlaps
   a conversation Nytka captured itself is left out and counted, unless the request asks for it.
2. Posting the same file again creates nothing and reports everything as already imported.
3. Imported conversations appear in the list by their Omi start time, are found by search, and are
   marked `source: "omi"` in the API.
4. Imported memories and tasks appear in their lists, linked to their conversations where Omi linked
   them.
5. No transcript text, memory text or file content reaches a log or an error message.

## The file

One JSON object (`omi-export.json`, from Omi's `GET /v1/users/export`), no audio. Nytka reads:

| Omi | Nytka |
|---|---|
| `conversations[]` with `discarded: false` | a conversation |
| `id` | `conversations.external_id` |
| `started_at`, `finished_at` (ISO 8601 with offset) | `started_at`, `ended_at`; `ended_at` is at least the last segment's end |
| `structured.title`, `structured.overview` | `ai_title`, `ai_summary`, `ai_status = 'done'` |
| `transcript_segments[]`: `text`, `start`, `end` (seconds from `started_at`), `speaker`, `is_user` | segments at `started_at + start` to `started_at + end`; `speaker` kept; `speaker_id` null (Omi's ids are per conversation, not voices) |
| `structured.action_items[]`: `description`, `completed`, `created_at` | tasks of that conversation |
| top-level `action_items[]` whose `conversation_id` was imported and whose text is not already one of that conversation's tasks | tasks of that conversation; items without an imported conversation are counted as skipped |
| `memories[]` with `is_dismissed` not true: `content`, `created_at`, `conversation_id` | memories, `source = 'omi'`, linked when that conversation was imported; text over 300 characters is cut at a word boundary |

Segment offsets below zero (Omi writes a few) are taken as zero. `skipped` counts every task or memory that was not created: a repeat of an
existing text, or a task without an imported conversation. Everything else (discarded conversations, geolocation, app results, chat messages, people, profile,
embeddings) is ignored. A conversation with no segment text is skipped and counted as `empty`.

## Behavior

**Schema** (`0010_import.sql`): `conversations` gains `source text not null default 'nytka'` (`nytka`
or `omi`) and `external_id text null`, unique on `(source, external_id)`. `segments.batch_id` becomes
nullable (an imported segment has no transcription batch). `memories.source` accepts `omi`. Task and
memory fingerprints are computed as for AI output, so duplicates inside the file collapse.

**One transaction per file.** A malformed file changes nothing. Conversations already present by
`(source, external_id)` are skipped whole, so a second run is a no-op.

**Overlap.** The same talk may have been recorded by both Omi and the pendant, so an Omi conversation
whose time range overlaps a `source = 'nytka'` conversation (it starts before that one ends and ends
after that one starts) is not imported and is counted in `overlapping`. `?overlapping=import` imports
those too. Its memories are still imported, unlinked; its tasks count as skipped. A conversation already imported counts as `alreadyImported`, whatever the query. Imported conversations are
`closed`, never merged with Nytka's own (`ConversationStore.AssignAsync` ignores `source <> 'nytka'`),
and publish no events: no webhooks, no memory extraction, no enrichment. Search picks them up
through the indexer as usual.

**Limits.** The body is at most 100 MB (`413` above). A body that is not an Omi export (no
`conversations` array) is `400` with a fixed message. A time without an offset is `400`.

**Re-enrichment.** Omi's titles and summaries are kept. `POST /api/v1/conversations/{id}/enrich`
(v0.2) still replaces them on request.

## API

| Call | Scope | Effect |
|---|---|---|
| `POST /api/v1/import/omi[?overlapping=import]` (body: the export file, `application/json`) | admin | `200 { conversations: { imported, alreadyImported, overlapping, discarded, empty }, segments, tasks: { imported, skipped }, memories: { imported, skipped } }`; `?overlapping=import` also imports the conversations that overlap Nytka's own (any other value is `400`) |
| `GET /api/v1/conversations`, `GET /api/v1/conversations/{id}` | read | items and detail gain `source` (`nytka` or `omi`) |

The README shows the `curl` command; the app has no import screen.

## Daily digest

Once a day the server writes a short account of the day: what happened, what was decided and what is
still open. It lands in `GET /api/v1/digests`, in a `digest.ready` webhook (so ntfy or n8n can push it)
and in the `list_digests` MCP tool.

**Settings.** `digest.enabled` (default `false`) and `digest.hour` (0 to 23, default `21`), so
`Nytka__Digest__Enabled` and `Nytka__Digest__Hour`. The local day and the hour use `user.timeZone`.

**Schedule.** The scheduler queues a `make-digest` job on the `Ai` lane, once per local date, when
`digest.enabled` is true, a model is configured, the local time is at or after `digest.hour` and that
date has no digest yet. The dedupe key is `make-digest:<yyyy-MM-dd>`. A restart or a late start still
builds the day's digest, as long as the local date has not changed.

**One read.** The job reads, in one place, the conversations that started on that local date and have a
title or a summary (id, local time, title, summary), the live tasks and the live memories created that
date (text only), and makes one `CompleteJsonAsync` call. A day with no such conversation is skipped:
no call, no row. Inputs are capped (80 conversations, 100 tasks, 100 memories, summaries cut to 600
characters). The prompt follows `ConversationPrompt`: output in `llm.outputLanguage`, times in the
user's zone, and nothing that the input does not say.

**Answer.**

```json
{ "headline": "", "overview": "", "highlights": [{ "text": "", "conversationId": "" }],
  "decisions": [""], "openQuestions": [""] }
```

`headline` is cut to 100 characters, `overview` is 2 to 4 sentences (cut to 1,000 characters), a list
holds at most 10 items of at most 300 characters. A highlight whose `conversationId` is not one of the
conversations in the input is dropped. An answer with an empty headline or overview is a failed run.

**Schema** (`0012_digests.sql`): `digests (id uuid pk, local_date date unique, headline, overview,
body jsonb, created_at)`; `body` holds `highlights`, `decisions` and `openQuestions`. The scheduled job
inserts with `on conflict (local_date) do nothing`, so the first digest of a date stays and a repeated
run makes no call and no event. A conversation deleted later leaves its id in the highlights; readers
treat a highlight whose conversation is gone as plain text.

**Event.** `digest.ready`, published in the insert's transaction, payload `{ id, localDate,
headline, overview }`. Like every event it is in `WebhookRecorder.Types`.

**Failure.** The job runner makes three attempts. After the third the job comes back an hour later
while its date is still the local today; a past date is dropped. Logs and errors say only what failed
(a status code or a fixed sentence), never the input or the digest text.

| Call | Scope | Effect |
|---|---|---|
| `GET /api/v1/digests?before=&limit=` | read | `{ items, nextBefore }`, newest date first; an item is `{ id, localDate, headline, overview, highlights, decisions, openQuestions, createdAt }`; `before` is a date (`yyyy-MM-dd`) and keeps earlier ones; `limit` defaults to 30, caps at 100 |
| `GET /api/v1/digests/{id}` | read | One item, `404` for an unknown id |
| `POST /api/v1/digests/run?date=yyyy-MM-dd` | admin | Queues a run for that local date that replaces its digest (a new id, a new `digest.ready`), whatever `digest.enabled` says: `202 { localDate }`. `400` for a missing, malformed or future date, `409` without a model. A day with no conversations still changes nothing. |

The MCP tool `list_digests` takes `before?` (a date) and `limit?` (1 to 100, default 30) and returns
what the list returns.

## Not in this version

- Omi audio: the export has none, and fetching it per conversation from Omi's cloud is not planned.
- Retiring the `omi-*` stack on the VPS and comparing its warehouse with the file (NYTKA-39, -42).
