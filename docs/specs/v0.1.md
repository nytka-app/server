# Nytka v0.1: capture

**Status: draft.** The whole picture lives in [../vision.md](../vision.md).

Version 0.1 proves the pipeline. Audio leaves the pendant, reaches your server, and comes back to the
app as transcripts. It adds no AI features beyond transcription. This spec covers both repositories,
`nytka-app/android` and `nytka-app/server`.

## Done when

1. A new user installs the APK, follows the first run with the README alone, and sees "Recording" in
   the app within five minutes.
2. Someone wears the pendant for a full day (8 hours or more) with the official Omi app uninstalled
   and the phone nearby. Every conversation appears in the list with its transcript. While the server
   is reachable, the transcript of new speech appears within three minutes. Diagnostics show under
   1% of Bluetooth packets lost.
3. With the phone in airplane mode for 30 minutes of talking, the queued audio uploads once the
   network returns, and those conversations appear with correct times.
4. A double tap mutes: the pendant gives one long buzz, and no frames enter the queue until the next
   double tap, which gives two short buzzes and resumes capture.
5. Deleting a conversation removes its segments and its audio from the server.
6. Killing the app, rebooting the phone or restarting the server loses no audio that reached the
   queue or the server. After a phone reboot, capture resumes when the pendant comes into range,
   without anyone opening the app.
7. Tagging `v0.1.0` in each repository produces a signed APK on GitHub Releases and an amd64 and
   arm64 image on GHCR, with CI green.

## Scope

**In:** pairing, reconnection and battery; background capture; mute from the notification and from a
double tap; upload with an offline queue; transcription and conversation splitting on the server;
the conversation list, the transcript view and deletion; server URL and token settings; the consent
step; developer-mode diagnostics; release pipelines for both repositories.

**Out:** titles, summaries, tasks and speaker labels; MCP; webhooks; memories and search; named
tokens and settings edited from the app; WebSocket; offline sync from pendant storage; import from
Omi; the Play listing; supporter keys; iOS.

## The pendant

This spec relies on these facts from the Omi repository (`BasedHardware/omi` at commit `2e34261`,
MIT, `omi/firmware/omi` and `sdks/device/PROTOCOL.md`), for consumer firmware 3.0.x.

| What | Where | Detail |
|---|---|---|
| Audio stream | service `19b10000-e8f2-537e-4f6c-d104768a1214`, notify `19b10001-e8f2-537e-4f6c-d104768a1214` | Opus, 16 kHz mono, 20 ms frames (320 samples), about 32 kbps VBR |
| Codec | read `19b10002-e8f2-537e-4f6c-d104768a1214` | `21` means Opus FS320. On any other value the app refuses to capture and says why. |
| Packet header | first 3 bytes of each notification | 2-byte little-endian counter that rises by one per notification, then a fragment index that restarts at 0 per frame |
| Button | notify `23ba7925-0000-1000-7450-346eac492e92` | 8 bytes; the first 4 hold a little-endian event code: 1 single tap, 2 double tap, 5 release |
| Haptic | write `cab1ab96-2ea5-4f4d-bb56-874b72cfc984` | `1`, `2` or `3` buzz for 100, 300 or 500 ms |
| Battery | standard `0x180F` / `0x2A19` | notified every 5 s while connected |
| Device info | standard `0x180A` | model, firmware and hardware revision |

The pendant drops audio while the phone stays connected without subscribing to the audio stream.
Nytka's mute relies on that behaviour.

Frame reassembly, as the firmware's `push_to_gatt` sends and the official app's `storeFramePacket`
reads: the firmware splits each encoded frame into notifications of at most `MTU - 3` bytes. The
counter rises by one for every notification, and the fragment index restarts at 0 for every frame.
Fragment 0 starts a new frame and completes the previous one. A counter that is not the previous
one plus one, or a fragment index that is not the previous one plus one, means lost notifications:
the app drops the partial frame and waits for the next fragment 0. The counter wraps from 65535 to
0, and the app treats that step as normal.

## Wire format

Media type `application/vnd.nytka.frames.v1`, little-endian. A chunk starts with a header:

| Field | Type | Meaning |
|---|---|---|
| `magic` | 4 bytes | ASCII `NYTK` |
| `version` | u8 | `1` |
| `codec` | u8 | `21` (Opus FS320) |
| `session` | 16 bytes | capture session UUID in RFC 9562 byte order (big-endian; in .NET read it with `new Guid(bytes, bigEndian: true)`, since `Guid.ToByteArray()` uses a different order) |
| `firstSeq` | u32 | sequence number of the first frame |
| `baseTime` | i64 | capture time of the first frame, in ms since the Unix epoch |
| `frameCount` | u32 | number of records that follow |

`frameCount` records follow: `offsetMs` (u32, capture time minus `baseTime`), `length` (u16), then
`length` bytes of Opus.

- The app starts a capture session (a new UUID, sequence from 0) each time its foreground service
  starts. Sequence numbers count delivered frames and have no holes. Capture times reveal the gaps.
- A frame's capture time is the phone's wall clock when the frame's last fragment arrived.
- A chunk holds at most 1,500 frames (30 seconds) and at most 512 KiB.
- WebSocket, when it arrives, carries the same bytes: one chunk per message.

## HTTP API v1

JSON uses camelCase, and times are ISO 8601 in UTC. Every request under `/api` carries
`Authorization: Bearer <token>`. Errors use RFC 9457 problem details.

| Method | Path | Result |
|---|---|---|
| GET | `/healthz` | No auth. 200 when the database answers, 503 otherwise. |
| GET | `/api/v1/info` | `{ serverVersion, apiVersion }`. The app's connection test and version check. |
| GET | `/api/v1/status` | `{ pendingChunks, oldestPendingAt, lastError }` for the status card and diagnostics. |
| POST | `/api/v1/chunks` | Stores one chunk (body `application/vnd.nytka.frames.v1`). |
| GET | `/api/v1/conversations?before=&limit=` | Newest first: `{ items: [{ id, startedAt, endedAt, status, preview }], nextBefore }`. `limit` defaults to 30 and caps at 100. |
| GET | `/api/v1/conversations/{id}` | `{ id, startedAt, endedAt, status, segments: [{ id, startedAt, endedAt, text }] }` |
| DELETE | `/api/v1/conversations/{id}` | Deletes the conversation with its segments and audio. 204. |
| GET | `/api/v1/conversations/{id}/transcriptions` | Raw transcription responses, for developer mode. |

Upload answers:

- `202 Accepted` with `{ acceptedThroughSeq }` when the server stored the chunk. The app then deletes
  those frames from its queue.
- `200 OK` with the same body when the server already holds a chunk with this session, `firstSeq`
  and `frameCount`. The app treats that as success.
- `409 Conflict` when the chunk overlaps stored frames with a different range.
- `400` for a malformed body, `401` for a bad token, `413` above 512 KiB.

### Diagnostics (added in 0.2.0)

`POST /api/v1/diagnostics` takes a JSON array of 1 to 500 samples, at most 256 KiB (`413` above,
`400` for a malformed body, more than 500 samples or a sample without `id` (UUID) or `at` (ISO 8601)).
The app sends link quality, queue and upload counters; a sample holds no audio, no transcript text,
no server URL and no token. Each sample is one row in `diagnostics` (`id`, `at`, `received_at`,
`payload` jsonb, the whole sample); a repeated `id` is ignored, so retries are safe. The answer is
`200 { accepted }`, the number of samples in the request. `GET /api/v1/diagnostics?since=&limit=`
returns `{ items, nextSince }`, samples after `since` oldest first; `limit` defaults to 500 and caps
at 5000, and `nextSince` is the `at` of the last item (null when there is none). The daily retention
job deletes samples older than 30 days. The API is additive, so `apiVersion` stays `1`.

The app compares `apiVersion` with its own and shows a banner when the major versions differ.
Version 0.1 serves `apiVersion: 1`.

### Pipeline

1. **Ingest.** The API checks the token and the chunk, stores the chunk as received in
   `audio_chunks`, and queues a `process-session` job.
2. **Decode and detect speech.** The job reads a session's unprocessed chunks in sequence order,
   decodes them to 16 kHz PCM and runs voice-activity detection. It keeps speech regions with 200 ms
   of padding and discards the rest. When a chunk is missing from the sequence, the job waits up to
   10 minutes for it and then carries on without it. At most one job per session runs at a time.
3. **Batch.** The job gathers speech into transcription batches. A batch closes after a one-second
   pause once it holds five seconds of speech, or when it holds 30 seconds of speech. Each batch keeps a map
   from its audio offsets back to capture times, because silence no longer sits between its regions.
4. **Transcribe.** A `transcribe` job sends the batch as a WAV file (16-bit PCM, 16 kHz, mono) to
   the configured endpoint as `multipart/form-data`: `file`, plus `model`, `language` and
   `response_format=verbose_json` when set. It adds `Authorization: Bearer <key>` when a key is
   configured. It reads `text` and `segments[]` (`start`, `end`, `text`) from the answer, and a
   response without segments becomes one segment covering the batch. It stores the raw answer for
   developer mode. Each request times out after 120 seconds. The job makes up to three attempts with
   backoff, then marks the batch failed and moves on. Version 0.1 sends one request at a time.
5. **Conversations.** A segment joins the open conversation unless it starts two minutes or more
   after that conversation's last speech. In that case the job closes the conversation and opens a
   new one. A timer job closes open conversations whose last speech is older than the gap, so a
   conversation ends even when no new audio arrives.
6. **Keep and forget.** After processing, the job stores the Opus frames that cover speech in
   `speech_audio` and deletes the chunk. A daily job deletes speech audio older than the retention
   setting. With retention 0, the job deletes the audio once its batch has a transcript.

A hosted service runs jobs from the `jobs` table with `FOR UPDATE SKIP LOCKED`. One process runs
everything, and v0.1 needs no message broker.

### Data

| Table | Holds |
|---|---|
| `capture_sessions` | `id`, `started_at`, `last_seq`, `last_frame_at` |
| `audio_chunks` | key `(session_id, first_seq)`, `frame_count`, `base_time`, `body` (bytea), `received_at`, `processed_at` |
| `conversations` | `id`, `started_at`, `ended_at`, `status` (`open` or `closed`), `created_at`, `updated_at` |
| `transcription_batches` | `id`, `conversation_id`, `started_at`, `ended_at`, `status` (`pending`, `done` or `failed`), `attempts`, `error`, `response` (jsonb) |
| `segments` | `id`, `conversation_id`, `batch_id`, `started_at`, `ended_at`, `text` |
| `speech_audio` | `id`, `conversation_id`, `started_at`, `ended_at`, `body` (bytea: a full chunk with header and records, so one parser reads both tables) |
| `jobs` | `id`, `kind`, `payload` (jsonb), `run_after`, `attempts`, `locked_until`, `last_error`, `created_at` |

Speech audio lives in Postgres, so one `pg_dump` backs up everything. At 32 kbps an hour of speech
takes about 14 MB. Move audio to files on a volume if the database outgrows that trade-off.

### Configuration

| Variable | Required | Default | Meaning |
|---|---|---|---|
| `ConnectionStrings__Postgres` | yes | | Postgres connection string |
| `Nytka__AdminToken` | yes | | Admin token of 32 characters or more. The server refuses to start without it. |
| `Nytka__Stt__Url` | yes | | Full URL of the transcription endpoint |
| `Nytka__Stt__ApiKey` | no | | Sent as a bearer token |
| `Nytka__Stt__Model` | no | | Sent as `model` |
| `Nytka__Stt__Language` | no | auto | Sent as `language` when set |
| `Nytka__Conversations__Gap` | no | `00:02:00` | Silence that ends a conversation |
| `Nytka__Audio__RetentionDays` | no | `14` | Days to keep speech audio; `0` deletes it after transcription |

The server logs no audio, no transcript text and no token, and it compares tokens in constant time.

Any OpenAI-compatible transcription endpoint fits: OpenAI, Groq, a LiteLLM gateway or a local
Whisper server. Servers with the whisper.cpp `/inference` shape accept the same `file` field, and
the plan verifies one of them (open question 4).

## App

### Modules

| Module | Holds |
|---|---|
| `:app` | UI (Compose, Material 3), navigation, Hilt wiring, notifications and settings |
| `:pendant` | companion-device pairing, the Bluetooth connection, frame reassembly, button, haptics and battery; no UI |
| `:core` | the frame queue (Room), chunking, the uploader and the API client (OkHttp, kotlinx.serialization) |

The Bluetooth and foreground-service code adapts the official Omi app's native Kotlin
(`app/android/app/src/main/kotlin/com/friend/ios/ble/`, MIT) and keeps its license notice. `:pendant`
exposes an interface, and a fake pendant implements it for tests and developer mode.

### Build

Kotlin with the Gradle Kotlin DSL and a version catalog. `minSdk` 31, `targetSdk` at the current
stable level, application ID `io.github.nytka_app`. Two flavors, `oss` and `play`: v0.1 publishes
`oss`, and `play` has to compile. CI runs ktlint and detekt next to the unit tests.

### Permissions

`BLUETOOTH_SCAN` (with `neverForLocation`), `BLUETOOTH_CONNECT`, `POST_NOTIFICATIONS`,
`FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_CONNECTED_DEVICE`, `INTERNET`, `RECEIVE_BOOT_COMPLETED`,
and the three companion-device permissions the official app declares:
`REQUEST_OBSERVE_COMPANION_DEVICE_PRESENCE`, `REQUEST_COMPANION_RUN_IN_BACKGROUND` and
`REQUEST_COMPANION_START_FOREGROUND_SERVICES_FROM_BACKGROUND`. The companion service requires
`BIND_COMPANION_DEVICE_SERVICE`. The app never requests `RECORD_AUDIO`.

### Capture

- Pairing uses `CompanionDeviceManager` with a filter on the Omi audio service. After association the
  app calls `startObservingDevicePresence`, and a `CompanionDeviceService` starts the foreground
  service (type `connectedDevice`) when the pendant appears.
- The service connects with `autoConnect`, reads the codec, and subscribes to audio, button and
  battery. It resubscribes when no audio arrives for four seconds, the same rule the official app
  uses.
- Each reassembled frame enters the Room queue with its session, sequence number and capture time.
- Every 30 seconds the service seals the queued frames into a chunk. The uploader sends sealed chunks
  in order and retries with backoff from 5 seconds to 5 minutes. A WorkManager job drains the queue
  when the service is not running and the network is up.
- The queue holds up to 1 GiB, about 70 hours of audio. Past 80% the app raises an alert, and at the
  cap it drops the oldest chunk (open question 2).
- Mute turns off audio notifications on the pendant, writes the haptic pattern (one 500 ms buzz for
  muted; two 100 ms buzzes 150 ms apart for live) and persists, so a reconnect stays muted.

### Screens

- **Top bar:** a status chip with a red dot while recording, grey while muted, and the pendant
  battery.
- **Conversations tab:** a status card (Recording or Muted, battery, server state, queued chunks and a
  Mute button) above conversations grouped by day, paged with `before` and refreshed by pulling down.
  Each row shows the time range, the length and a preview.
- **Conversation screen:** date, time range and length, then segments as timestamped paragraphs. The
  overflow menu holds Delete, with a confirmation, and in developer mode Raw transcription.
- **Device tab:** a pendant card (name, connection, battery, firmware, Mute, Forget), a server card
  (URL, state, API version, queue, last upload), Settings (server URL, token, private-network switch)
  and About (the version; seven taps unlock developer mode).
- **First run:**
  1. Server URL and token, with a connection test.
  2. Nearby-devices and notification permissions.
  3. The consent step: "Recording people without their consent is illegal in some places. You are
     responsible for following the law where you use Nytka."
  4. Pairing.
- **Developer mode:** Bluetooth packet rate and loss, queue size, sealed chunks, the last upload
  result, server status, a fake-pendant switch that replays a bundled recording, a button that saves
  the next 60 seconds of frames as a test fixture, and Copy debug report (app and Android versions,
  device model, settings without the token, recent errors).

### Notifications

- The foreground notification (channel "Recording", low importance) reads "Recording · 82% · 0
  queued" and offers Mute or Unmute.
- Alerts (channel "Alerts") fire when the pendant has been disconnected for 5 minutes, the server has
  been unreachable for 15 minutes, or the pendant battery reaches 20%. Developer mode can change the
  thresholds.

### Network rules

The app requires `https://` unless the private-network switch is on. Android cannot switch cleartext
per server at runtime, so the network security config permits cleartext and the app enforces HTTPS
in its own code. The token sits in DataStore, encrypted with a key from the Android Keystore.

## Tests and release

- **Server:** unit tests for the frame parser, batching and conversation splitting; API and pipeline
  tests against Postgres (Testcontainers) with a fake transcription endpoint; a replay test that feeds
  a recorded session through the whole pipeline.
- **App:** unit tests for reassembly, the queue, chunking and the uploader's retries. The fake pendant
  drives the capture path in tests.
- **CI, both repositories:** build, tests, lint, gitleaks and the noreply-email check. The Android
  workflow builds both flavors.
- **Release:** release-please opens a release PR from conventional commits. Merging it tags the
  version, and the tag builds a signed APK (keystore in repository secrets) or a multi-arch image and
  publishes it to GitHub Releases or GHCR.

## Open questions

1. VAD parameters and batch thresholds (one-second pause, five-second minimum, 30-second maximum),
   tuned on real recordings.
2. The queue-full policy: drop the oldest chunk (current choice) or stop capture.
3. The 10-minute wait for a missing chunk.
4. Whether a whisper.cpp-style `/inference` endpoint accepts the request as specified.
