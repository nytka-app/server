# Nytka v0.6 (speakers): which lines are mine, and who the others are

Nytka stores who spoke each line and lets you name the voices around you. The recognition itself
(voiceprints) stays with the transcription provider for now; Nytka reads what the provider says and
adds names on top. Voice recognition inside Nytka, so that it works with any provider, is a later
version.

## Done when

1. A transcription answer that carries `speaker_id` and `is_user` for a segment has both stored, and
   a segment without them stores nulls.
2. A conversation's segments carry `speaker`, `speakerId`, `isUser`, `personId` and `personName`.
3. Naming a voice (`POST /api/v1/people` with `speakerId`) shows the name on every past and future
   segment of that voice; deleting the person brings the provider's labels back.
4. The summary, task and memory prompts and the MCP transcript label the wearer's lines `Wearer` and
   a named voice by its name.

## Behavior

**Provider fields.** `TranscriptionClient` reads `speaker_id` like `speaker` (a string, or an integer
taken as its decimal string, at most 64 characters) and `is_user` as a JSON boolean. Anything else is
null. `is_user` null means the provider did not say.

**Voices are `speaker_id`s.** An anonymous label such as `SPEAKER_00` can mean different people in
different batches, so only a `speaker_id` links to a person. A segment with a label and no id can
never be named.

**People.** `people` holds a name (1 to 80 characters, unique ignoring case). `person_voices` maps a
`speaker_id` to one person; a person can own several voices, so a second cluster of the same
person joins the first under the same name. Segments resolve through `person_voices` when read
(migration `0009_speakers.sql`), so nothing is rewritten when a name changes.

**Label rule** (server code, one place per read path): `isUser` wins, then the person's name, then
the provider's `speaker`.

## What the model writes

Baseline: only 38% of summaries, 28% of tasks and 17% of memories were useful, and UTC times in the
prompts produced invented deadlines. Three changes to the prompts and the pipeline:

**Local time (NYTKA-31).** The setting `user.timeZone` (`Nytka__User__TimeZone`, an IANA id such as
`Europe/Kyiv`, default `UTC`) sets the zone the prompts use. Transcript lines `[HH:mm:ss]` and the
`Date:` line (now with the weekday) are rendered in it, for the summary and the memory run; the MCP
transcript stays UTC. The system prompt names the zone, tells the model to resolve "tomorrow" or
"Friday" against the conversation's local date and never to invent a deadline nobody said. An
unknown id falls back to UTC.

**Tighter tasks and memories (NYTKA-32).** A task is only what the wearer committed to do or was
asked to do and did not turn down, anchored on the `Wearer` label; other people's tasks, loose ideas
and finished work are out, and with no `Wearer` line only what is clearly addressed to the wearer
counts. A memory is only a lasting fact about the wearer, stated or confirmed by them; facts about
other speakers and one-off events are out. The JSON schemas are unchanged.

**Short conversations (NYTKA-33).** Under 20 words a conversation is still skipped (`ai_status`
`skipped`). From 20 to 59 words (`BriefWords` = 60, about 25 seconds of speech) it gets a title and a
one-sentence summary, no tasks, and no memory run (the run is recorded `done` without a model call).

## API

| Call | Scope | Effect |
|---|---|---|
| `GET /api/v1/people` | read | `{ items: [{ id, name, createdAt, voices, segments }] }`, by name |
| `POST /api/v1/people` `{ name, speakerId? }` | admin | Without `speakerId`, the person. With it, the voice takes the name; a voice named before moves. 201 for a new person, 200 for an existing name |
| `PATCH /api/v1/people/{id}` `{ name }` | admin | Rename; a name another person has is 409 |
| `DELETE /api/v1/people/{id}` | admin | Removes the person and their voice links; segments keep provider labels |
| `DELETE /api/v1/people/{id}/voices/{speakerId}` | admin | Unlinks one voice (a wrong guess) |

## Not in this version

- Voiceprints, enrollment and matching inside Nytka: the 0.9 goal. Until then, labels are only as
  stable as the provider makes them; the maintainer's `stt` service keeps `speaker_id` across
  chunks.
- Deleting a voiceprint: it lives in the provider, so `stt`'s own `speakers.py forget` does it.
- App screens: the app reads the new segment fields and names a voice from the transcript.
